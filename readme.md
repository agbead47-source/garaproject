# 개발요청서 분석·변환 도구 – UI 가안 (Flask)

> To-do 팀 화장품 무역 대시보드 중 **주제 3번** 기능의 UI 프로토타입.
> 이 파일을 프로젝트 루트에 두고, AI에게 "PLAN.md를 읽고 N단계만 진행해줘"처럼 단계별로 요청한다.

---

## 1. 기능 한 줄 요약
발주업체(해외 고객사)에게 받은 **개발요청서**를 업로드하면, 핵심 항목을 자동으로 뽑아내고
**연구소용 / 공장용** 내부 전달 문서로 나눠 변환하며, 원하는 **언어로 번역**해 주는 도구.

## 2. 이번 가안의 범위 (중요)
- **UI만 구현한다.** 실제 문서 분석, OCR, 번역, AI API 호출은 하지 않는다.
- 어떤 파일을 올려도 **미리 준비한 더미 분석 결과**를 보여준다.
- API 키, DB, 외부 네트워크 호출 **사용 금지**.
- `python app.py` 한 번으로 실행되고 http://127.0.0.1:5000 에서 확인 가능해야 한다.
- 나중에 실제 기능으로 교체할 자리는 함수로 분리하고 `# TODO: 실제 연동` 주석을 단다.

## 3. 기술 스택
- Python 3.10+, Flask (requirements.txt에는 `flask` 한 줄)
- Jinja2 템플릿 + 순수 CSS + 약간의 바닐라 JS
- 빌드 도구, 프론트엔드 프레임워크 사용하지 않음
- 아이콘이 필요하면 이모지 또는 CDN 사용

## 5. 공통 레이아웃 (base.html)
- 우측 하단에 **무역 도우미** 💬 버튼 (로그인 화면 제외. 26번 참고)
- 좌측 사이드바: 서비스 로고(텍스트 "To-do Trade"), 메뉴
- 메뉴는 **해외영업 실제 업무 순서**대로 번호를 붙여 세운다.
  - **업무 흐름**
    1. 신규 바이어 발굴 (18번)
    2. 개발요청서 분석 (6번·16번)
    3. 일정관리 (19번)
    4. AI 샘플 미리보기 (12-3)
    5. 영업단가 계산 (14번)
    6. 고객사 관리 (12-4·17번)
  - **참고 · 기록** — 🌍 국가별 규제 검색 / 📈 오늘의 트렌드 / 🕘 처리 이력
- 규제·트렌드·이력은 흐름의 한 단계가 아니라 어느 단계에서나 들여다보는 화면이라 따로 묶었다.
- 상단바: 현재 페이지 제목, 우측에 사용자명 "해외영업팀 홍길동" + 로그아웃
- 진행 단계 표시(스텝퍼): `① 업로드 → ② 분석 결과 → ③ 변환·번역` — 현재 단계 강조

## 6. 화면 상세

### 6-1. 문서 업로드 (`/`)
> 파일이 없을 때 쓰는 **직접 작성** 경로는 16번 참고.

- 드래그앤드롭 업로드 박스 (PDF, DOCX, XLSX, JPG/PNG 안내 문구)
  - 파일을 올리면 파일명과 용량만 표시 (서버에서 내용은 사용하지 않음)
- **"샘플 개발요청서로 체험하기"** 버튼 (파일 없이도 진행 가능)
- 옵션 입력 영역
  - 고객사 선택: 드롭다운 (더미 고객사 목록)
  - 전달 대상: 체크박스 `🧪 연구소 (개발 의뢰)` / `🏭 공장 (생산 검토)` (기본 둘 다 체크)
    - 요청서를 그대로 보내지 않고 받는 쪽 문서로 바꿔 보낸다는 안내를 같이 띄운다 (6-3 참고)
  - 출력 언어: 드롭다운 `한국어(기본)` / `English` / `中文` / `Tiếng Việt`
- "분석 시작" 버튼 → 2초 로딩 화면("문서를 읽는 중… → 항목 추출 중…") 후 `/result` 로 이동
  - 로딩은 JS setTimeout으로 연출만 한다

### 6-2. 분석 결과 (`/result`)
- 상단 요약 카드 4개
  - 문서 언어 감지: English
  - 추출 항목 수: 19
  - 확인 필요 항목: 5 (주황색 강조)
  - 규제 주의 성분: 1 (빨간색 강조, 성분별 EU 판정에서 자동 산출)
- 좌우 2단 구성
  - **왼쪽: 원문 미리보기** — 더미 영문 개발요청서 텍스트를 스크롤 박스로 표시
  - **오른쪽: 추출 항목 표** — 컬럼: `항목 | 추출 값 | 신뢰도 | 상태`
    - 신뢰도는 막대 또는 % 뱃지
    - 상태: `확인됨`(초록) / `확인 필요`(주황) / `누락`(회색)
    - 행을 클릭하면 왼쪽 원문에서 해당 문장에 형광펜 하이라이트 (JS)
    - 추출 값은 **읽기 전용** — 원문에서 읽어낸 그대로 둔다
      (고치는 자리는 변환 화면 한 곳뿐이다. 6-3 참고)
- 하단 **"성분별 규제 판정" 표** (실데이터)
  - 컬럼: `성분 | INCI | 요청 함량 | 역할 | 허용 기준·근거 | 판정`
  - 행을 클릭하면 왼쪽 원문에서 해당 문장이 강조된다 (추출 항목 표와 동일 동작)
  - 카드 제목에 `🇪🇺 EU 실데이터` / `더미` 뱃지와 법령 기준일 표기
- 그 아래 경고 박스 — 주의·사용 불가 성분만 모아 보여준다 (없으면 "걸리는 성분 없음")
  - "규제 검색으로 이동" 버튼은 `/regulation` 으로 연결 (같은 앱 안이라 활성화)
- 하단 버튼: `이전` / `내부 전달 문서 만들기 →`

### 6-3. 내부 전달 문서 변환 (`/convert`)
요청서를 **그대로 돌리지 않습니다.** 받는 쪽이 쓰는 문서로 바꿔서 보냅니다.
연구소용에는 단가가 없고, 공장용에는 처방이 없습니다.

- 탭 2개: **🧪 연구소 · 개발 의뢰** / **🏭 공장 · 생산 검토**
- 연구소 문서 섹션
  - 제품 개요 (제품명, 유형, 타깃 국가)
  - 제형·사용감 요청 (텍스처, 향, 색상)
  - 필수 성분 / 배제 성분(Free-from) 목록
  - 인증·클레임 요구 (Vegan, Cruelty-free 등)
  - 시험 요청 (안정성, 피부자극 등)
  - 규제 주의사항
- 공장 문서 섹션 — **"이 조건으로 만들 수 있습니까"** 를 묻는 문서다
  - 제품 사양 (제품명, 용량, 용기·부자재, **용기 사급/자급**)
  - 발주 수량 (MOQ)
  - 생산·출고 일정 (샘플 납기, 본생산 선적)
  - 포장·라벨 요구사항
  - 서류·책임자

#### 고객사 소개 — 해외영업이 설명해 주는 자리
문서를 받는 쪽은 **고객사를 모릅니다.** 왜 무향을 고집하는지, 인증서를 왜 매번
원본으로 요구하는지 모르면 같은 질문이 영업으로 다시 돌아옵니다.
그래서 두 문서 맨 앞에 고객사 소개가 붙습니다.

- **자동으로 채워지는 것** — 고객사 관리(12-4)에 등록돼 있으면 국가·등급·거래 시작·
  누적 발주·특징 태그를 끌어옵니다. 등록되지 않은 곳이면 등록 링크를 띄웁니다
- **받는 쪽에 맞춰 고릅니다** — 그 고객사가 매번 요구하는 것 중
  연구소에는 `제형·성분`·`서류·인증`, 공장에는 `패키지`·`납기·선적`·`서류·인증` 만 싣습니다.
  연구소는 DHL 착불 계정을 알 필요가 없습니다
- **영업 담당자 코멘트** — 이 건에서만 특별히 알아둘 점을 직접 적는 칸

#### 값은 그 자리에서 고칩니다
변환된 문서의 값은 **클릭하면 바로 수정**됩니다.
고치는 자리는 여기 한 곳입니다 — 분석 결과(6-2)는 원문을 읽어낸 기록이라 손대지 않습니다.
자동 변환이 문장을 어색하게 만들거나, 영업이 한 줄 덧붙여야 할 때가 있기 때문입니다.
고친 값은 노란색으로 표시되고, 복사·전달에 그대로 반영됩니다.

고친 값은 **실제로 저장됩니다** (`doc_edit_store.py` → `data/doc_edits.db`).
새로고침해도 남고, 도구 줄의 **↺ 수정 되돌리기**를 누르면 자동 변환 값으로 돌아갑니다.

- 저장 단위는 `원본파일|문서종류|언어` 입니다. 한국어 문서에 적은 문장이
  영문 문서에 끼어들면 안 되기 때문에 언어까지 키에 넣습니다
- 연구소 문서와 공장 문서는 서로 다른 문서라, 코멘트도 따로 답니다
- 고친 값만 저장합니다. 원래 값은 저장하지 않습니다 —
  변환 결과가 바뀌면 그 위에 다시 덮이면 되고, 되돌리기는 저장한 줄을 지우는 것입니다
- 저장 경로: `POST /api/doc-edit` (한 칸), `POST /api/doc-edit/reset` (문서 단위 되돌리기).
  빈 값으로 저장하면 그 칸은 자동 변환 값으로 돌아갑니다

#### 공장에 왜 보내나 — 그리고 무엇을 안 보내나
"공장은 생산인데 개발요청서를 왜 받나"는 당연한 의문이라 여기 적어 둡니다.

공장에 가는 건 개발요청서가 아니라 **생산 가능성 검토 요청**입니다.
아래 항목은 연구소 작업이 끝나기를 기다리면 늦습니다.

| 항목 | 늦으면 생기는 일 |
|---|---|
| 용기 사급/자급 | 고객 지정 용기가 충전 라인에 안 물리면 일정이 통째로 밀린다 |
| MOQ | 최소 생산 단위에 안 맞으면 요청 자체를 되돌려야 한다 |
| 본생산 선적일 | 생산 슬롯을 역산해 잡아야 한다 |
| 필요 서류 | CoA·MSDS는 생산·출하 단계 산출물이다 |

반대로 **목표 단가·거래조건·선적 조건은 공장에 보내지 않습니다.**

국가별 규제 검색의 **EU 판정만** 실제 법령 데이터로 동작합니다.
API 키·계정·유료 구독이 필요 없고, 외부 호출은 수집 스크립트를 돌릴 때만 일어납니다.
(2번의 "화면에서 외부 API 호출 금지" 규칙은 그대로 지킵니다 — 화면은 로컬 SQLite만 읽습니다.)

### 13-1. 데이터 출처
| 단계 | 엔드포인트 | 인증 |
|---|---|---|
| 최신 통합본 찾기 | EU Publications Office SPARQL (`publications.europa.eu/webapi/rdf/sparql`) | 불필요 |
| 법령 전문 받기 | EU Cellar (`publications.europa.eu/resource/celex/{CELEX}`) | 불필요 |

화장품 규정 **Regulation (EC) No 1223/2009**의 최신 통합본을 받아
Annex II(사용 금지) / III(사용 제한) / IV(색소) / V(방부제) / VI(자외선 차단제) 표를 파싱합니다.
현재 기준 **성분 2,381건 / 검색용 이름 8,579건**이 적재됩니다.

> CosIng 웹사이트에도 CSV 내려받기가 있지만 백엔드가 브라우저 앱 밖에서는 열리지 않아
> 자동 수집에 쓸 수 없습니다. 위 두 엔드포인트가 같은 법령의 공식 원문입니다.

### 13-2. 사용법
```bash
python regdata/sync_eu.py            # 최초 1회 (캐시 있으면 재사용)
python regdata/sync_eu.py --refresh  # 법령 개정 후 갱신 (주 1회 정도면 충분)
```
- 결과물: `regdata/regulation.db` (SQLite, 약 1.2MB) — `.gitignore` 대상, 언제든 다시 만들 수 있음
- 추가 패키지 없음 (표준 라이브러리만 사용, `requirements.txt` 그대로)
- **DB가 없으면 EU도 자동으로 더미로 돌아갑니다.** 스크립트를 안 돌려도 앱은 그대로 실행됩니다.

### 13-3. 판정 규칙 (`reg_store.py`)
성분표에서 읽은 함량과 부속서 허용 기준을 비교합니다.

| 상황 | 판정 |
|---|---|
| Annex II 등재 (예외 용도 없음) | 🔴 사용 불가 |
| 요청 함량 > 최대 허용 농도 | 🔴 사용 불가 |
| 제품 유형별로 기준이 갈리는 구간 | 🟠 주의 |
| 함량을 못 읽음 / 기준이 수치가 아닌 조건문 | 🟠 주의 |
| 허용 기준 이내 | 🟢 적합 |
| Annex II~VI 미등재 | 🟢 적합 (개별 제한 없음) |
| 성분표에 "미사용 / Free-from" 표기 | 🟢 적합 (판정 대상 아님) |

화면에서는 행마다 `실데이터` / `더미` 뱃지를 달아 구분하고,
행을 펼치면 근거 부속서 번호·법령 기준일·데이터 출처를 보여줍니다.

실데이터를 붙이면서 더미의 오류도 드러났습니다. 예를 들어 레티놀 EU 기준은
더미에 "리브온 0.05% 이하"로 적혀 있었지만, 실제 Annex III No.376은
**바디로션 0.05% / 그 외 리브온 0.3%** 입니다. (요청 0.5%는 두 기준 모두 초과)

### 13-4. 아직 더미인 것
- 🇺🇸 미국 — 화장품 허용 농도 양성목록 자체가 없음(색소·OTC 모노그래프만 예외)이라
  API가 있어도 "허용 기준" 칸을 채울 수 없습니다. openFDA 화장품 엔드포인트는 부작용 신고 데이터입니다.
- 🇰🇷 한국 — data.go.kr MFDS 오픈API 3종(사용제한 원료정보·원료성분정보·규제정보)으로 붙일 수 있으나 **서비스키 발급 필요**
- 🇯🇵 일본 — e-Gov 법령API는 키 없이 열리지만, 화장품기준은 고시(告示)라 e-Gov 법령검색에 없습니다
- 🇨🇳 중국 / 🇻🇳 베트남 — 공개 API 없음. IECIC·ACD Annex 문서를 수기 적재해야 합니다

### 13-5. 주의
자동 판정은 **참고용**입니다. 근거 규정과 법령 기준일을 화면에 남기도록 만들었지만,
최종 판단은 RA 담당자가 원문을 확인해야 합니다.

## 14. 영업단가 계산 (`/pricing`)

해외영업 실무 흐름을 그대로 따릅니다.

```
구매팀 원가표 → (선적조건별 물류비 + 적하보험) → 영업마진 → 환율 → 결제통화 판매 단가
```

영업이 원가를 직접 쌓는 게 아니라 **구매팀이 준 원가를 받아서** 거기에 조건을 얹는 구조입니다.
계산은 전부 브라우저(JS)에서 실시간으로 하고, 서버는 기본값만 내려줍니다.

### 14-1. 화면 흐름
**① 구매팀 원가** — 원가산출서(XLSX/CSV/PDF)를 드래그하면 항목을 인식해 채웁니다.
파일 없이 눌러도 샘플 원가표로 진행됩니다. 인식된 값은 그대로 수정할 수 있고,
읽었지만 계산에 못 쓰는 행(금액 누락, 1회성 금형비 등)은 **"인식하지 못한 행"**으로 따로 보여줍니다.

원가표에 **없던 비용은 직접 더합니다.** `＋ 원가 항목 추가` 로 줄을 만들고
이름·금액을 넣으면 제조원가 합계에 바로 들어갑니다. 자주 쓰는 항목은 골라 쓰면
이름과 메모가 채워집니다 — 용기·부자재(자급) / 단상자·라벨 / 금형 상각 /
검사·시험비 / 내륙 운송 / 기타.

인식하지 못한 행에는 **`계산에 넣기`** 버튼이 있습니다. 누르면 그 이름으로
원가 줄이 만들어지고 금액만 넣으면 됩니다. 금형비처럼 "개당 배분 여부를 확인해야
하는" 비용이 그냥 버려지지 않게 하려는 자리입니다.

직접 넣은 줄은 ✕ 로 지울 수 있고, `기본값으로 되돌리기` 를 누르면 같이 사라집니다.
지우면 `계산에 넣기` 버튼도 **되살아납니다.** 금액을 잘못 적어 지우는 일이 흔한데,
버튼이 `추가됨` 으로 굳으면 다시 넣을 방법이 없습니다.

**② 선적 조건·물류비** — EXW / FCA / FOB / CFR / CIF.
조건을 바꾸면 판매가에 포함되는 비용 범위가 달라지고, 빠지는 항목은 흐리게 표시됩니다.

| 비용 | 구간 (고칠 수 있음) | 포함 시작 조건 |
|---|---|---|
| 내륙 운송 | 공장 → 부산항 | FCA |
| 수출 통관·서류 | | FCA |
| THC·터미널 핸들링 | 부산항 | FOB |
| 해상 운임 | 부산 → LA | CFR |
| 적하보험료 | | CIF |

**구간은 화면에서 고칩니다.** 내륙 운송이 늘 부산항인 것도, 해상 운임이 늘 LA 로
가는 것도 아닙니다. 인천에서 로테르담으로 가는 건이면 그렇게 적습니다.
구간은 계산에 쓰이지 않습니다 — 나중에 이 화면을 다시 봤을 때
"어느 노선 기준으로 뽑은 단가인지" 를 알아보려고 적어 두는 칸입니다.

적하보험료 = **CFR 금액 × 부보율(110%) × 요율(0.12%)** — 무역 실무의 표준 계산식입니다.

**물류비 항목도 더 넣을 수 있습니다.** 예상 못 한 부대비용이 늘 생깁니다.

| 미리 넣어 둔 것 | 포함 시작 조건 |
|---|---|
| 서류·인증 발급 (C/O·FTA 증명) | FCA |
| 팔레트·훈증 처리 (IPPC) | FCA |
| 보세창고 보관료 | FOB |
| 검량·검수·컨테이너 검사 | FOB |
| 유류·통화 할증료 (BAF·CAF) | CFR |
| 체선·체화료 (Demurrage) | CFR |
| 기타 | 이름을 직접 적습니다 |

금액만 받지 않고 **어느 조건부터 판매가에 포함되는지**를 같이 받습니다.
이게 안 맞으면 EXW 단가에 해상 운임이 얹히는 식으로 틀어집니다.
넣은 뒤에도 줄에서 바로 바꿀 수 있고, 조건에서 빠지는 줄은 흐려집니다.

견적서에는 물류비가 단가에 녹아 들어갑니다. 항목 이름은 사내에서만 봅니다.

**③ 영업마진** — 판매가 대비(Margin) / 원가 대비(Markup) 두 방식을 토글로 고릅니다.
같은 25%라도 결과가 다릅니다 (CIF 기준 2,566원 vs 2,406원).

**④ 결제 통화 · 환율** — 파는 통화를 고르고, 그 통화의 견적 환율과 목표 단가를 넣습니다.

미국만 상대하는 게 아닙니다. 일본은 엔화, 유럽 유통사는 유로로 달라는 곳이 있고,
국내 벤더를 통한 간접 수출이면 원화로 끊기도 합니다.

| 통화 | 소수 자리 | 메모 |
|---|---|---|
| USD · EUR · CNY · HKD · SGD · GBP · AUD | 2 | |
| JPY | 0 | 시장은 100엔 단위로 고시하지만 여기서는 1엔 기준 |
| KRW | 0 | 원화로 끊으면 환율 변동 위험이 없다 |

- 통화를 바꾸면 **그 통화의 기본 환율로 갈아 끼웁니다.** 손으로 고친 환율이 남아 있으면
  엔화에 1,385원이 붙는 식으로 엉뚱한 단가가 나옵니다. 바뀌었다고 토스트로 알리고,
  목표 단가도 다시 확인하라고 적습니다 (목표 단가는 고객이 말한 숫자라 **자동 환산하지 않습니다**)
- 통화에 따라 **소수 자리가 달라집니다.** 엔화 단가에 소수점이 붙으면 견적서가 어색해집니다
- **원화(KRW)를 고르면** 환율 변동 표와 손익분기 환율 카드를 숨깁니다.
  환율 위험이 없는 거래에 환율 시나리오를 그리면 없는 위험을 만드는 셈입니다
- 환율은 여전히 **수기 입력**입니다 (실시간 환율 API 연동 자리에 TODO)

견적서도 고른 통화로 나갑니다. 단가·합계·조건별 단가·원화 환산 표기가 모두 따라갑니다.
단가는 그 통화의 최소 단위로 확정해서 **단가 × 수량 = 합계**가 정확히 맞습니다
(JPY 276 × 5,000 = 1,380,000).

아래는 그 다음 이야기입니다.

### 14-2. 결과
- **판매 단가** (USD·KRW) + 목표 단가 대비 갭 — 초과하면 카드가 빨강
- **조건별 단가표** — EXW~CIF 5단계를 한 번에 보여줘 견적서에 그대로 옮길 수 있음
- **📄 견적서 만들기** — 계산 결과를 그대로 견적서 문서로. 고객 발송용(영문)·사내 보관용(국문) 두 벌 (14-5)
- **원가 구성** — 제조원가 / 물류비 / 보험 구분, 미포함 항목도 0원으로 표시
- **환율 변동 시 단가** — ±10% 시나리오
- **환율 손익분기점** ← 핵심

### 14-3. 환율 손익분기점
원가는 원화, 판매는 달러라 **환율이 내려가면(원화 강세) USD 단가가 올라갑니다.**

```
필요 최저 환율 = 판매가(KRW) ÷ 목표 단가(USD)
목표 단가로 팔 때 실제 마진 = 1 − 총원가 ÷ (목표단가 × 현재환율)
```

기본값(CIF·5,000개·마진 25%·환율 1,385원)에서는 **916원**이 손익분기 환율이라 469원 여유가 있고,
목표 USD 2.8로 팔면 실제 마진은 50.4%입니다.

### 14-4. 기본값 시나리오
구매팀 원가 1,570원(사급 기준) 기준:

| 조건 | 판매 단가 | 목표 USD 2.8 대비 | 손익분기 환율 |
|---|---|---|---|
| **CIF** (기본) | USD 1.85 | 0.95 여유 ✅ | 916원 (+469 여유) |
| FOB | USD 1.65 | 1.15 여유 ✅ | 815원 |
| EXW | USD 1.51 | 1.29 여유 ✅ | 748원 |
| 환율 1,100원 | USD 2.33 | 0.47 여유 ✅ | 916원 (+184 여유) |
| 자급(부자재 +1,420원) | USD 3.22 | 0.42 초과 ❌ | 1,594원 **(209원 부족)** |

마지막 줄이 실무 포인트입니다. 자급으로 바꾸면 손익분기 환율이 현재 환율을 넘어서서,
목표 단가로 팔면 마진이 25% → **13.7%**로 깎이는 게 바로 보입니다.

### 14-5. 견적서 (`/pricing/quote`)
계산만 해 놓고 결국 다시 엑셀로 옮겨 적는 일이 없도록,
**판매 단가 카드 아래 `📄 견적서 만들기`** 버튼을 두었습니다.

```
영업단가 계산 → 견적서 만들기(창) → 고객 발송용(영문) ↔ 사내 보관용(국문) → 인쇄 · PDF 저장
```

**문서는 두 벌입니다.** 고객사로 나가는 문서에 우리 원가가 드러나면 안 되기 때문입니다.

| | 고객 발송용 (`?view=customer`) | 사내 보관용 (`?view=internal`) |
|---|---|---|
| 언어 | 영문 (QUOTATION) | 국문 (견 적 서) |
| 단가 | USD 단가·합계만 | USD + **원화 환산·견적환율** |
| 조건별 단가 | **없음** | EXW~CIF 참고표 |
| 품목명 | 영문명 | 국문명 + 영문명 |
| 담당자 | `QUOTE_CONTACT_EN` (영문 표기) | 사내 계정명 |

원화 환산·견적환율·조건별 단가(EXW 1.51 ~ CIF 1.85)는 **마진과 원가 구조가 드러나는 값**이라
고객 발송용에서는 아예 렌더링하지 않습니다(`build_quote(form, view)` 에서 값 자체를 비웁니다).
사내 보관용 화면에는 *"고객사로 보내지 마세요"* 경고를 띄웁니다.

**만들기 창** — 지금 화면의 단가·수량·선적 조건이 그대로 들어가고,
문서에 적을 값(수신처·담당자·품목명 국문/영문·인도 장소·유효기간·결제조건·납기·원산지·포장·비고)만
확인합니다. **수신처와 담당자는 고객사 관리(20번)에 등록된 값에서 고릅니다** —
고객사를 고르면 그 회사 담당자가 역할과 함께 드롭다운에 뜨고, 대표 담당자가 기본으로 잡힙니다.
고른 담당자의 이름과 이메일이 견적서 수신란(`Attn.` / `E-mail`)에 들어갑니다.
등록되지 않은 곳이면 `직접 입력`으로 타이핑할 수 있습니다. 거래조건 값은 **고객에게 그대로 나가는 계약 문구라 영문**이고,
무슨 뜻인지 한글 설명을 입력칸 아래에 붙여 두었습니다. 기본값은 `dummy_data.QUOTE_TERMS` 에 있습니다.

**견적서 문서** — 견적번호(`QT-YYYYMMDD-####`)·견적일자, 수신/공급자, 품목 1행, 합계,
거래 조건표, 유의사항 순입니다. 두 가지를 실무 기준으로 맞췄습니다.
- 견적 단가는 **센트 단위로 확정** — `단가 × 수량 = 합계`가 고객 쪽 계산과 어긋나지 않습니다
- 거래조건은 **지명까지** — `CIF` 가 아니라 `CIF Los Angeles` (인도 장소 없이는 견적이 성립하지 않습니다)

**회사 직인** — 문서 하단 서명란(`TO-DO TRADE CO., LTD. / Kim Moo-yeok, CEO (Seal)`) 옆에
직인(`static/seal.svg`)이 겹쳐 찍힙니다. 인쇄·PDF 저장에서도 색이 빠지지 않도록
`print-color-adjust: exact` 를 걸어 두었습니다.

> 직인과 공급자 정보(상호·사업자번호·주소·대표이사·영문 표기)는 **가안용 더미**입니다.
> `dummy_data.SELLER` 한 곳만 바꾸고 `static/seal.svg` 를 스캔한 실제 직인으로 교체하면 됩니다.

### 14-6. 아직 더미인 것
- 원가표 인식 — `parse_cost_sheet()` 한 곳만 실제 XLSX/CSV 파싱으로 바꾸면 됩니다
- 환율 — 수기 입력. 통화별 기본값도 더미입니다. 실시간 환율 API 연동 자리에 TODO를 달아 두었습니다
- 직접 넣은 원가 항목 — 화면에서만 삽니다. 새로고침하면 사라집니다
- 운임·보험요율 — 포워더 견적표를 받아 채워야 합니다
- 공급자 정보·직인 — `dummy_data.SELLER` + `static/seal.svg` 교체
- 견적서 보관 — 지금은 만들어 보여주기만 하고 저장하지 않습니다 (처리 이력 연동 자리)
- 견적서 파일 — 브라우저 인쇄로 PDF를 뽑습니다. 메일 첨부용 PDF·엑셀 다운로드는 아직 없습니다

## 15. 오늘의 트렌드 - 성분 관심도 실시간 연동 (`/trends`)

키워드 랭킹은 더미로 두고, **성분 관심도만 실시간 API**로 바꿨습니다.

### 15-1. 출처
| 항목 | 출처 | 인증 |
|---|---|---|
| 성분 관심도 | **Wikimedia Pageviews API** (`wikimedia.org/api/rest_v1/`) | 불필요 |
| EU 규제 상태 | 13번에서 만든 규제 DB 재사용 | — |
| SNS·커머스 언급량 | 더미 | 무료 공개 API 없음 |

영문 위키백과의 성분 문서 조회수를 **관심도 대리 지표**로 씁니다.
판매량이 아니고, 성분명이 다의어이거나 화장품 외 뉴스가 터지면 왜곡될 수 있어
화면에도 그 한계를 적어 두었습니다. (그래서 Peptide 같은 다의어 성분은 목록에서 뺐습니다)

SNS 언급량은 무료 공개 API가 없습니다. 연동하려면 유료 소셜 리스닝 서비스가 필요합니다.

### 15-2. 캐시 (레이트리밋 때문에 필수)
연속 10여 건이면 429가 떨어져서 디스크 캐시를 둡니다.

```bash
python trend_store.py          # 캐시 워밍업 (12종 전부, 429 나면 백오프 후 재시도)
python trend_store.py --force  # TTL 무시하고 다시 수집
```
- 캐시: `trenddata/pageviews.json` (TTL 12시간, `.gitignore` 대상)
- 화면 로딩 시 오래된 항목을 **한 번에 3건만** 새로 받아 페이지가 느려지지 않게 합니다
- 못 받은 성분은 가짜 값을 넣지 않고 `미수집`으로 표시합니다
- 화면 우측 상단 **새로고침** 버튼(`?refresh=1`)으로 강제 갱신

### 15-3. 화면 (분석 전용)
- 순위 · 성분(INCI) · 카테고리 · **최근 14일 스파크라인**(인라인 SVG) · 일평균 · 증감률
- **EU 규제 상태**를 같은 표에 붙였습니다 — "뜨는 성분인데 EU에서 쓸 수 있나"가 한 줄에서 보입니다
- 요약 카드: 수집 성분 수 / 최다 상승 / 최다 하락
- 우측 "상승·하락" — 증감률 상위·하위 3종

실제 수집 예시 (2026-09-18 기준):

|---|---|---|---|---|
| 1 | 살리실릭애씨드 | 987 | +12.1% | 조건부 사용 (Annex III No.98) |
| 2 | 히알루론산 | 583 | −14.1% | 제한 없음 |
| 6 | 레티놀 | 364 | −10.2% | 조건부 사용 (Annex III No.376) |
| 11 | 알부틴 | 63 | +12.2% | 조건부 사용 (Annex III No.378 · 7%) |
| 12 | 나이아신아마이드 | 57 | +78.7% | 제한 없음 |

### 15-4. 분석 전용 화면
트렌드는 "여기서 뭘 만들자"까지 가지 않고 **보는 화면**으로 둡니다.

- 성분별 순위·스파크라인·증감률·EU 규제 상태
- **카테고리별 관심도** — 기능군(브라이트닝/진정/장벽…) 단위로 묶은 평균 증감

- 상승·하락 상위 3종

## 16. 개발요청서 직접 작성 (`/compose`)

고객사 요청이 늘 파일로 오지는 않습니다. 메일·전화·미팅으로 받은 내용을
**해외영업 담당자가 사내 양식에 직접 적어 연구소·공장으로 넘기는** 경로입니다.

```
[파일 업로드] ─┐
               ├→ 내부 전달 문서(연구소용·공장용) → 전달
[직접 작성]  ─┘
```

업로드 화면(`/`)에서 "직접 작성해서 개발팀에 넘기기"로 들어갑니다.

### 16-1. 요청 구분 — 고객사 건만 있는 게 아니다
해외영업이 트렌드·시장조사를 보고 **스스로 발의**하는 경우도 많아서,
요청이 어디서 시작됐는지를 먼저 고릅니다.

| 구분 | 쓰는 상황 | 고객사 칸 |
|---|---|---|
| **고객사 요청** | 받은 요청을 사내 양식으로 정리 | 드롭다운에서 선택 |
| **자사 기획** | 트렌드·시장조사 기반 자체 발의 | 없음 → `자사 기획 (해외영업팀)` |
| **신규 고객 제안** | 아직 거래 없는 곳에 먼저 제안 | 회사명 직접 입력 (미정이면 비워 둠) |

고른 값에 따라 고객사 칸이 바뀌고, 전달 문서 머리말의 **요청 주체**도 따라 바뀝니다.
트렌드에서 불러오면 자동으로 `자사 기획`이 선택됩니다.

**요청·기획 배경** 칸도 뒀습니다. "왜 이 제품인지"를 적어 두면 연구소가 우선순위를 잡기 쉬워서,
연구소용 문서의 제품 개요에 그대로 실립니다.

### 16-2. 작성 폼 (5개 묶음 + 성분표)
| 묶음 | 항목 |
|---|---|
| 📌 기본 정보 | 요청 구분\*, 고객사, 요청·기획 배경, 제품명\*, 제품 유형\*, 용량, 용기, 용기 사급/자급 |
| 🧪 제형·사용감 | 텍스처, 향, 색상, 벤치마크 제품 |
| 🏷 클레임·시험 | 인증·클레임, 배제 성분, 안정성 시험, 피부자극 시험 |
| 💰 수량·거래조건 | MOQ, 목표 단가, 거래조건, 샘플 납기, 본생산 선적, 선적 조건 |
| 🌍 판매 국가·서류 | 판매 국가\*, 필요 서류, 책임자 지정, 패키지 디자인, 라벨 |

\* 필수. 안 채우면 제출이 막히고 해당 칸이 주황으로 표시됩니다.

자주 쓰는 값 10개(용량 30ml, 무향, Free-from, MOQ 등)는 미리 채워 두고 `자동` 뱃지를 답니다.

### 16-3. 성분 입력 + 실시간 EU 판정
성분표는 행을 추가·삭제할 수 있고, `성분명 / INCI / 함량 / 역할`을 넣습니다.

**입력을 멈추면 0.45초 뒤 서버에 판정을 물어봅니다** (`POST /api/judge`).
13번에서 만든 EU 규제 실데이터로 대조해서 오른쪽 패널에 바로 뜹니다.

```
Retinol 0.5%  → 사용 불가  (a) 0,05 % (b) 0,3 % — 최대 허용 0.3% 초과
Niacinamide 5% → 적합      개별 제한 없음 (Annex 미등재)
```

요청서를 쓰는 중에 "이 성분 이 농도 EU에서 되나?"를 바로 확인할 수 있습니다.

### 16-4. 트렌드에서 불러오기
`/compose?ingredient=<성분키>` 로 들어가면 트렌드 성분이 프리필됩니다.
(오늘의 트렌드 화면에는 링크를 두지 않고, 주소로 열 수 있게만 남겼습니다)

- 제품명·유형·텍스처를 카테고리별 제형 틀로 채움
- 주 성분 + 방부제를 성분표에 넣되 **규제 한도 안쪽 함량**으로 (레티놀 0.2%, 알부틴 2.0% 등)
- 상단에 `불러옴` 칩으로 출처와 관심도 수치 표기

### 16-5. 전달 문서로 변환
"개발팀 전달 문서 만들기"를 누르면 `/convert` 로 갑니다.

- 작성한 값이 연구소용·공장용 문서에 **그대로** 들어갑니다 (필드 key를 맞춰 뒀습니다)
- `규제 확인` 항목은 성분 판정 결과에서 **자동 생성**됩니다
  (예: `Retinol 0.5% — EU 기준 초과`)
- 직접 쓴 문장은 번역 사전에 없으므로 언어를 바꿔도 그대로 실립니다
- 문서 상단에 `영업 직접 작성` 뱃지, 스텝퍼는 `① 직접 작성 → ③ 변환·전달` 2단계로 바뀝니다

### 16-6. 새로 생긴 API
```
POST /api/judge   {"ingredients": [{"name","inci","amount","role"}, ...]}
  → {"ingredients": [... status/limit/rule/note ...], "live": true, "flagged": 1}
```
규제 DB가 없으면 `live: false` 로 내려가고 화면은 "판정할 수 없음"을 표시합니다.
(가짜로 "적합"을 만들지 않습니다)

## 17. 메일 번역·요약 (`/projects/<id>/contacts` → 주고받은 메일)

> 원래 고객사 화면의 이메일 탭에 있었습니다. 메일은 회사가 아니라 **그 건**에
> 딸린 것이라 프로젝트의 바이어 연락으로 옮겼습니다 (30번 참고).

받은 메일을 펼치면 **🌐 번역 / ✂️ 요약** 버튼이 나옵니다.
둘의 성격이 달라서 버튼에 출처를 같이 적어 두었습니다.

| 기능 | 처리 방식 | 인증 |
|---|---|---|
| 번역 | **MyMemory Translation API** (Open API) | 불필요 |
| 요약 | 자체 처리 (외부 전송 없음) | — |

### 17-1. 번역 — MyMemory Open API
```
GET https://api.mymemory.translated.net/get?q=<문장>&langpair=en|ko
```
- 한글 비율로 원문 언어를 판별해 **en↔ko 자동 방향 설정**
- MyMemory는 **한 요청 500자 제한**이라 문장 단위로 쪼개 보내고 결과를 합칩니다
- 무료 쿼터가 있어 **문장 단위로 디스크 캐시**(`apicache/translations.json`)
  - 같은 메일 두 번째 조회는 0.00초 (실측)
- 원문·번역문을 **좌우로 나란히** 보여줍니다
- 일부 문장이 실패해도 그 문장만 원문을 남기고 나머지는 번역합니다

실제 결과:
```
MOQ is 5,000 units and our target unit price is 2.8 per piece.
→ MOQ는 5,000단위이며 목표 단가는 개당 2.8단위입니다.

레티놀 농도를 0.3%로 낮춰 주세요.
→ Reduce the retinol concentration to 0.3%.
```

### 17-2. 요약 — 자체 처리
무료로 쓸 수 있는 **키 없는 요약 API가 없어서** 로컬에서 처리합니다.
(LibreTranslate·HuggingFace 모두 키를 요구합니다)

메일 본문을 외부로 보내지 않는다는 장점이 있어 화면에도 그렇게 표시했습니다.

1. **핵심 문장 3개 추출** — 무역·개발 키워드(MOQ·단가·납기·승인·규제 등) 가중치,
   질문 문장 가산, 인사말·서명 제외
2. **항목 추출** — 수량 / 단가 / 용량 / 농도 / 기간 / 시점을 정규식으로
3. **성분 EU 규제 대조** — 농도 앞 1~3단어를 후보로 잡아 규제 사전에서 가장 긴 이름을 찾고,
   13번 EU 실데이터로 판정

실제 결과 (Glowtree Beauty 메일):
```
· Our legal team flagged the Retinol 0.5% for the EU expansion.
· Could you propose an alternative that works for both US and EU?
· Also, please share how much the unit price would change.

항목: 농도 Retinol 0.5% · 수량 5,000 · 단가 USD 2.8
🇪🇺 [사용 불가] Retinol 0.5%  — (a) 0,05 % (b) 0,3 % · Annex III No.376
```

메일을 읽자마자 **"레티놀 0.5%는 EU에서 못 쓴다"**가 근거와 함께 뜹니다.

### 17-3. 새로 생긴 API
```
POST /api/translate  {"text": "...", "source": "en", "target": "ko"}
  → {"text", "segments":[{source,translated,cached,ok}], "failed", "cached", "provider"}

POST /api/summarize  {"text": "..."}
  → {"sentences", "facts", "ingredients", "total_sentences", "method":"local"}
```

### 17-4. 이 프로젝트가 쓰는 외부 Open API 정리
| API | 쓰는 곳 | 인증 |
|---|---|---|
| EU Publications Office SPARQL | 규제 통합본 번호 조회 (13번) | 불필요 |
| EU Cellar | 화장품 규정 전문 (13번) | 불필요 |
| Wikimedia Pageviews | 성분 관심도 (15번) | 불필요 |
| MyMemory Translation | 메일 번역 (17번) | 불필요 |

## 18. 신규 바이어 발굴 (`/prospects`)

> **범위 주의** — 이 모듈만 외부 수집과 로컬 SQLite를 씁니다.
> 2번의 "UI만·DB 없음" 규칙은 기존 기능에 계속 적용되고, 이 모듈에는 적용하지 않습니다.

해외 브랜드의 공개 제품정보와 자사 제조·개발 역량을 비교해 조사 우선순위와
제안 근거를 만들고, 후속 연락까지 관리합니다.

```
자사 역량 등록 → 후보 등록·CSV → 허용된 공식 페이지 수집 → pandas 정리
  → OEM/ODM 적합도 → 제안 가설 선택 → 제안 초안 → 담당자가 연락 → 결과 기록
```

### 18-1. 화면
| 경로 | 내용 |
|---|---|
| `/prospects` | 후보 목록. 요약 4종, 검색·필터, 적합도/최근/다음 연락일 정렬, CSV 입출력 |
| `/prospects/<id>` | 상세 5탭: 기업 개요 · 제품 목록 · 적합도 · 제안 기회 · 연락 이력 |
| `/company-capabilities` | 자사 역량 (대응 방식·제품군·제형·MOQ·인증·납기) |
| `/prospects/<id>/proposal` | OEM/ODM × 한국어/영어 제안 초안 |
| `/prospect-followups` | 오늘·기한 지남·예정·완료 |
| `/prospects/analytics` | 퍼널·경로별·국가별 분포·회신 소요기간 · **엑셀 내려받기** |
| `/prospects/import` | CSV 미리보기 → 오류 확인 → 저장 |

### 18-2. 설명 가능한 적합도
```
확인 가중치 = 일치 및 불일치 기준의 가중치 합
정보 확인율 = 확인 가중치 / 전체 가중치 × 100
적합도      = 일치 기준 가중치 합 / 확인 가중치 × 100   (확인 가중치 0이면 NULL)
```

| 기준 | OEM | ODM |
|---|---:|---:|
| 제품군 대응 | 30 | 25 |
| 생산 사양 / 개발 요구 대응 | 20 | 30 |
| 주문량과 MOQ | 20 | 15 |
| 명시된 인증 요구 대응 | 15 | 15 |
| 명시된 납기 요구 대응 | 15 | 15 |

- 값은 **일치 / 불일치 / 미확인** 셋뿐입니다. 고객이 밝히지 않았으면 미확인입니다.
- 확인율 50% 미만은 **정보 부족**으로 표시하고 확정 추천에서 제외합니다.
- 점수와 확인율은 **항상 함께** 표시합니다. 수주 확률이 아닙니다.
- MOQ·인증 불일치는 총점과 별개로 `필수조건 불일치`로 강조합니다.
- 규칙 버전(`2026-09-19.v1`)과 채점 시각을 저장합니다.

### 18-3. 자사 역량은 왜 있나

적합도는 한쪽만으로 못 냅니다. **바이어가 원하는 것**과 **우리가 할 수 있는 것**을
맞대야 나옵니다. `/company-capabilities` 는 그 뒤쪽입니다.

이 값이 없으면 점수가 낮아지는 게 아니라 **점수가 아예 안 나옵니다.**
비교할 상대가 없으니 다섯 기준이 전부 `미확인` 이 되고, 확인 가중치가 0이라
적합도는 `NULL` 입니다.

| 우리 쪽에 있어야 하는 것 | 없으면 판정 못 하는 기준 | OEM | ODM |
|---|---|---:|---:|
| 제조 가능 제품군 | 제품군 대응 | 30 | 25 |
| 개발 가능 제형·특징 | 생산 사양 / 개발 요구 대응 | 20 | 30 |
| 제품군별 MOQ | 주문량과 MOQ | 20 | 15 |
| 보유 인증 | 명시된 인증 요구 대응 | 15 | 15 |
| 양산 납기 | 명시된 납기 요구 대응 | 15 | 15 |

그래서 화면 위에 **지금 상태로 몇 점어치를 판정할 수 있는지**를 적어 둡니다.
"MOQ 가 비어 있어 20점어치 기준을 판정 못 합니다" 처럼 빈 칸과 그 결과를
같이 보여 줍니다. 말로 "등록해 주세요" 라고 쓰는 것보다 이쪽이 알아듣기 쉽습니다.

역량을 고치면 후보 점수를 **전부 다시 계산합니다** (`rescore_prospect`).
지난 점수가 옛 기준으로 남아 있으면 순위를 믿을 수 없습니다.

### 18-4. 분석 결과 내려받기 (`/prospects/analytics.xlsx`)

실적 보고용입니다. 화면을 캡처해 붙이면 **정의가 같이 안 따라갑니다.**
"상담 전환율 23%" 한 줄만 옮겨지면 어느 기간인지, 고유 기업 기준인지,
실제인지 데모인지가 사라집니다. 다음 회의에서 숫자를 다시 설명하게 됩니다.

그래서 숫자와 집계 조건·정의를 **같은 파일 안에** 담습니다. 네 장입니다.

| 시트 | 담는 것 |
|---|---|
| 요약 | 집계 조건(데이터 구분·기간·기준일·적합도 기준) + 지표 |
| 발굴 경로별 | 경로별 후보·첫 연락·회신·상담 |
| 국가별 적합도 | 소재국별 후보 수·평균 적합도·평균 확인율 |
| 지표 정의 | 각 지표의 정의와 읽을 때 주의할 점, 기준별 가중치 |

화면에서 고른 **기간·OEM/ODM 기준·실제/데모**를 그대로 따릅니다.
파일 이름에도 적습니다 — `발굴분석_실제_90일_2026-09-19.xlsx`.

지키는 것:
- 값이 없으면 **빈 칸**입니다. 0 으로 채우지 않습니다
  (연락한 기업이 0이라 못 구한 전환율과, 정말 0%인 전환율은 다릅니다)
- 못 구한 비율은 숫자 칸에 0 을 넣지 않고 **`계산 불가`** 라고 적습니다
- 실제와 데모를 한 파일에 섞지 않습니다
- 화면에 없는 값을 만들어 넣지 않습니다. 같은 집계를 그대로 옮깁니다

후보 목록 자체는 기존 CSV(`/prospects/export.csv`)로 받습니다.

### 18-5. 데이터 수집 — **미완료**
수집 기계장치는 만들었지만, **이용조건을 확인해 수집이 허용된 출처를 아직 확보하지 못했습니다.**
명세 11절 3단계 기준으로 이 단계는 완료가 아닙니다. CSV 입력만으로 크롤링 완료라고 하지 않습니다.

구현해 둔 것 (동작 확인 완료):
- URL 안전 검사 — `http/https` 만 허용, localhost·사설 IP·링크 로컬·`file://` 차단, **리다이렉트 대상 재검증**
- `robots.txt` 게이트 — 우리 User-Agent 에게 허용된 경로만. 읽기 실패 시 보수적으로 차단
- 401·403 우회 안 함 / 429 는 `Retry-After` 따라 최대 2회 재시도 후 중단
- JSON-LD(schema.org Product) 파싱 — beautifulsoup4 가 없어 표준 라이브러리 `HTMLParser` 로 구현
- JS 렌더링 페이지는 "자동 수집 미지원"으로 남기고 CSV 입력 안내
- 실패해도 기존 제품 데이터를 지우거나 더미로 바꾸지 않고, 실행 기록에 실패 사유를 남김

남은 일: 대상 사이트의 이용조건을 검토해 `sources.collection_allowed` 를 `allowed` 로 기록한 뒤
실제 레코드를 1곳 이상에서 수집하는 것.

### 18-6. pandas 처리
- 회사명·국가·제품군·INCI 표준화 (원문 보존)
- 가격/용량은 숫자와 통화·단위를 분리. 못 읽으면 **NULL 로 두고 0·USD 로 보정하지 않음**
- 중복 제거는 `(후보, 제품 URL)` 처럼 명확한 기준만. 이름 유사성으로 회사를 합치지 않음
- `groupby` 로 기업별 제품 수·제품군·성분 빈도 집계
- 도메인이 같은 묶음만 **중복 후보**로 표시하고, 통합은 담당자가 판단

## 19. 일정관리 (`/schedule`)

> **범위 주의** — 18번과 마찬가지로 이 모듈은 로컬 SQLite(`data/schedule.db`)에 실제로 값을 저장합니다.
> 2번의 "UI만·DB 없음" 규칙은 나머지 화면에 계속 적용됩니다.

메뉴 흐름에서 **3번 자리**입니다.
개발요청을 넘긴 뒤 샘플·피드백·단가·발주·선적까지, 해외영업이 실제로 쫓기는 건 문서가 아니라 **날짜**입니다.

```
개발요청 전달 → 규제·처방 검토 → 샘플 제작 → 샘플 발송 → 고객 피드백
  → 단가 확정 → 본생산 발주(PO) → 본생산 → 선적·서류
```

### 19-1. 화면
| 경로 | 내용 |
|---|---|
| `/schedule` | 요약 5종 + 네 가지 보기 + 건 목록 |
| `/schedule?view=agenda` | **할 일** (기본) — 기한 지난 일정을 맨 위에 모으고, 오늘부터 14일치를 날짜별로 |
| `/schedule?view=timeline` | **타임라인** — 건별 막대 + 단계 점. 세로 점선이 오늘 |
| `/schedule?view=calendar` | **캘린더** — 월 격자. 이전/이번/다음 달 이동 |
| `/schedule?view=certs` | **인증서** — 만료일·갱신 착수일 관리 (31번) |
| `/schedule/new` | 건 등록. 착수일·리드타임을 고르면 9단계 일정 초안을 미리 보여줌 |
| `/schedule/<id>` | 단계별 일정. 완료·날짜 변경·추가·삭제, 다음 화면 링크 |

### 19-3. 일정 상태
```
D+n  기한 지남      계획일이 지났는데 완료 표시가 없음
오늘  오늘 할 일
D-n  임박(3일 이내) / 예정
완료  done_date 기록. 계획보다 늦게 끝났으면 며칠 늦었는지 같이 표시
```
- 건 상태(진행 중·보류·완료·중단) 중 **완료·중단 건의 일정은 요약·캘린더에서 세지 않습니다.**
- 건 색(빨강·주황·초록)은 지연 여부로 정합니다. 수주 확률이 아닙니다.
- 기준 시간대는 **Asia/Seoul** 이고 화면에 표시합니다.

### 19-4. 한 단계가 밀리면 뒤도 밀린다
실무에서 제일 잦은 일이라 기본 동작으로 넣었습니다.
날짜를 바꿀 때 **이후 단계도 함께**(기본 켜짐)를 두면 뒤 단계가 같은 일수만큼 이동합니다.
- 이미 **완료한 단계는 움직이지 않습니다.**
- 끄면 그 일정 하나만 바뀝니다.
- 날짜 형식(YYYY-MM-DD)이 아니면 아무것도 바꾸지 않고 안내만 합니다.

### 19-5. 화면 사이 값 전달
일정관리가 흐름의 가운데라서, 앞뒤 화면과 값을 주고받습니다.

| 어디서 | 어디로 | 넘기는 값 |
|---|---|---|
| 신규 바이어 발굴 상세 | `/compose` | 회사명 · 국가 · 요청 구분(신규 제안) |
| 신규 바이어 발굴 상세 | `/schedule/new` | 회사명 · 국가 · 후보 id |
| 신규 바이어 발굴 상세 | `/regulation` · `/pricing` | 국가 · 회사명 |
| 내부 전달 문서 변환 | `/schedule/new` | 제품명 · 고객사 · 판매 국가 |
| 일정 상세 | `/compose` · `/regulation` · `/sample` · `/pricing` · `/customers` | 제품명 · 회사명 · 국가 |

- 넘어간 값은 **채워만 둡니다.** 화면에 "넘어온 값을 미리 채웠다"고 적고, 나머지는 그 화면의 기본값 그대로입니다.
- 회사명이 등록된 고객사면 드롭다운에서 고르고, 아니면 **신규 제안**으로 두고 직접 입력 칸에 넣습니다.
  이름이 비슷하다는 이유로 고객사에 붙이지 않습니다.
- 영업단가 화면은 **건 이름·고객사만** 바뀝니다. 원가·물류비는 그 건의 실제 값이 아니라고 화면에 적어 둡니다.

### 19-6. 저장·안전

## 20. 고객사 담당자 (`/customers/<id>` → 👤 담당자 탭)

고객사 한 곳에 담당자는 한 명이 아닙니다. 발주를 넣는 **구매 담당**, 성분표·CoA·인증서를
요구하는 **품질 담당**, 선적 서류를 챙기는 **물류 담당**이 따로 있고,
**메일을 누구에게 보내느냐로 회신 속도가 갈립니다.**
그래서 담당자를 목록으로 들고 역할과 대표 담당자를 함께 관리합니다.

담당자만 **SQLite(`data/contacts.db`)에 실제로 저장**됩니다. 나머지 고객사 정보는 아직 더미입니다.

### 20-1. 역할
| 역할 | 무엇을 보내는 창구인가 |
|---|---|
| 🛒 구매·발주 | 발주(PO)와 단가 협의 |
| 🧪 개발·제형 | 처방·샘플 피드백 |
| 🔬 품질·인증 | 성분표·CoA·인증서 |
| 🚢 물류·선적 | 선적 일정과 서류 |
| 💳 대금·결제 | 인보이스·송금 |
| 👤 기타 | 그 밖의 담당 |

### 20-2. 할 수 있는 것
- **추가·수정** — 이름(필수)·직함·역할·이메일·전화·시차·사용 언어·메모
- **대표 담당자 지정** — 고객사 목록 카드와 상세 상단에 나오는 한 명. 고객사당 정확히 한 명입니다
- **비활성 / 복구** — 담당이 바뀌어도 **지우지 않습니다**. 주고받은 메일의 상대가 누구였는지가 남아야 하니까요
- **삭제** — 잘못 넣은 행을 지우는 용도. 삭제 확인창에서 비활성을 먼저 권합니다
- **검색** — 고객사 목록에서 담당자 이름·이메일로도 회사를 찾습니다

대표 담당자를 비활성으로 돌리거나 삭제하면 **남은 활성 담당자 중 한 명이 대표를 이어받습니다.**
(대표가 비어 있는 고객사가 생기지 않도록)

## 21. 최신 규제 소식 수집 (`/regulation` 상단)

규제 판정(성분별 허용 기준)은 20번까지의 `reg_store` 가 EU 법령으로 합니다.
이 기능은 그 **앞단**입니다 — 성분 기준이 바뀌기 전에 **공지가 먼저 뜨기** 때문에,
"규제가 곧 바뀐다"는 신호를 판정보다 먼저 보는 자리입니다.

업로드받은 `regulation_crawler.py` 를 `regnews_store.py` 로 옮겨 화면에 연결했습니다.

### 21-1. 동작
```
SOURCES 의 규제기관 페이지 → 링크 제목에 키워드가 든 것만 추출
  → 처음 보는 링크만 '신규' 표시 → newsdata/ 에 누적
```

2026-09-19 에 **실제로 열어 보고 맞춘 주소**입니다.

| 지역 | 기관 · 게시판 | 키워드 | 상태 |
|---|---|---|---|
| 🇰🇷 한국 | 식약처 · 입법/행정예고 | 화장품 | ✅ |
| 🇰🇷 한국 | 식약처 · 제·개정 고시 | 화장품 | ✅ |
| 🌏 해외 | 식약처 · 해외 규정 개정 소식 | 화장품 | ✅ |
| 🇪🇺 EU | European Commission (DG GROW) 뉴스 | cosmetic, annex, cmr, omnibus, fragrance allergen | ✅ |
| 🇮🇩 인도네시아 | BPOM | kosmetik, cosmetic, halal | ✅ |
| 🇺🇸 미국 | FDA | — | ⛔ 차단 |

### 21-2. 실제로 붙여 보고 고친 것

**기관 대문이 아니라 공지 목록 페이지여야 합니다.** 처음에는 기관 대문 주소를 썼는데,
식약처·EU 모두 결과가 **메뉴 링크로 전부 덮였습니다**(식약처 대문에서 잡힌 20건이 전부 메뉴).

그래서 `list_selector` 를 뒀습니다 — 목록이 들어 있는 영역만 훑습니다.
식약처는 `div.bbs_list01` 이고, 이걸 지정하니 메뉴가 통째로 빠집니다.
비워 두면 예전처럼 페이지 전체를 봅니다.

**키워드는 좁아야 합니다.** 식약처 게시판은 식품·의약품·의료기기가 섞여 있어서
`기능성`·`원료` 를 넣으면 `건강기능식품 기능성 원료…` 공지가 딸려 옵니다(실측).
`화장품` 하나면 기능성화장품·맞춤형화장품·화장품법이 전부 걸립니다.

**공지 날짜가 붙었습니다.** 목록 한 줄(`li`/`article`/`tr`)에서 `<time datetime>` 을 먼저 보고,
없으면 그 줄의 날짜 모양을 찾습니다. 식약처는 `공지 2026-08-18` 이 그대로 나옵니다.

**FDA 는 자동 수집을 차단합니다.** 어떤 주소로 요청해도 `abuse-detection-apology.html`
로 보냅니다. 기관이 막아 둔 것이라 **우회하지 않고 꺼 뒀습니다**(`enabled: False`).
FDA 소식은 기관이 제공하는 이메일 구독을 쓰는 게 맞습니다.

**BPOM 은 제목에 군더더기가 붙습니다.** 링크 텍스트가
`13 Jul 2026 Dilihat 6852 kali BPOM Intensifkan…` 이라 `title_strip` 으로 앞부분을 뗍니다.

### 21-3. 사이트별로 조절하는 값
| 키 | 하는 일 |
|---|---|
| `list_selector` | 목록 영역. 이 안의 링크만 본다 (메뉴 제외) |
| `min_title` | 제목 최소 길이. 국문은 짧아 6, BPOM 은 메뉴 라벨을 거르려 25 |
| `title_strip` | 제목 앞 군더더기(날짜·조회수) 제거 정규식 |
| `enabled` | `False` 면 수집하지 않는다 (FDA) |
| `note` | 화면 출처 칩에 뜨는 안내 |

사이트마다 HTML 구조를 분석하지 않고 **링크 텍스트 + 키워드**로 거르기 때문에
디자인이 바뀌어도 잘 안 깨집니다. 대신 메뉴·안내 링크가 섞일 수 있어서,
**어떤 키워드에 걸렸는지**를 항목마다 같이 보여줍니다.

수집 예절은 원본 스크립트 그대로 지킵니다.
- **robots.txt 확인** — 수집을 막아 둔 페이지는 건너뛰고 사유를 표시
- **사이트 간 3초 대기**, 요청 타임아웃 15초
- 기관마다 최대 40건, 저장소에는 최대 300건까지만 보관

### 21-4. 실행
```
python regnews_store.py            # 수집
python regnews_store.py --dry-run  # 저장하지 않고 결과만 확인 (URL 바꿀 때)
```
화면에서는 규제 화면의 **🔄 지금 수집** 버튼으로도 돌립니다 (십여 초 걸립니다).

결과는 두 가지로 떨어집니다. 둘 다 `newsdata/` 아래이고 저장소에는 올라가지 않습니다.
- `regulation_news.json` — 화면이 읽는 저장소 (누적·신규 판정용)
- `regulation_news.csv` — 엑셀에서 열어보는 용도 (utf-8-sig)

### 21-5. 화면
- 마지막 수집 시각 · 확인 건수 · 신규 건수
- **수집하지 못한 곳**을 사유와 함께 따로 표시 (접속 차단 / HTTP 오류 / robots.txt)
- 항목마다 기관 · 수집일 · 걸린 키워드, 클릭하면 원문 새 탭

### 21-6. 확인한 것
로컬 픽스처 페이지로 수집 로직을 검증하고, **실제 사이트로도 확인했습니다.**
```
키워드 없는 링크 제외 (메뉴·다른 분야 공지)   PASS
중복 링크 제외                              PASS
두 번째 수집에서 신규 0건 (누적 동작)         PASS
CSV 출력 (엑셀 한글)                        PASS
접속 실패한 기관의 사유 기록·표시             PASS
수집 이력이 없을 때 빈 화면 안내              PASS
국문 제목 수집 (식약처 픽스처)                PASS
짧은 국문 제목 통과 ('화장품법 개정' 7자)      PASS
```

국문 사이트를 붙이면서 **인코딩 버그를 하나 잡았습니다.** 응답 헤더에 charset 이 없으면
`requests` 가 본문을 ISO-8859-1 로 읽어서 국문 제목이 깨지고 키워드가 하나도 안 걸립니다.
`res.text` 대신 `res.content`(바이트)를 BeautifulSoup 에 넘겨 해결했습니다.
영문 기관만 볼 때는 드러나지 않던 문제입니다.

**윈도우 콘솔에서도 하나 잡았습니다.** 기본 cp949 로는 수집한 제목에 섞인
en dash(`–`) 같은 글자에서 `UnicodeEncodeError` 로 스크립트가 통째로 멈춥니다.
CLI 시작할 때 stdout/stderr 을 UTF-8 로 돌려놓습니다
(`_force_utf8_console()`). 리눅스에서는 드러나지 않던 문제입니다.

**실제 사이트 수집 결과 (2026-09-19)**
```
식약처 · 입법/행정예고          2건  ← 화장품 표시·광고 실증 / 기능성화장품 심사 개정고시안
식약처 · 제·개정 고시           0건  (그날 화장품 건이 없었음 - 정상)
식약처 · 해외 규정 개정 소식     0건  (〃)
European Commission (DG GROW)  0건  (〃)
BPOM                          3건
FDA                          차단  (수집하지 않음)
```
0건인 곳은 고장이 아니라 **그날 화장품 공지가 없었던 것**입니다.
식약처 입법/행정예고가 이 기능의 핵심입니다 — 규제가 바뀌기 전 예고 단계라
가장 먼저 뜹니다.

- **FDA** — 차단이라 수집 불가. 이메일 구독이나 공식 데이터 제공 경로를 알아봐야 합니다
- 중국 NMPA·일본 후생노동성·베트남 DAV 추가
- 국가별 규제 판정(`reg_store`)과의 연결 — 공지에 나온 성분이 우리 처방에 있는지 대조

## 22. 국가별 화장품 수출입 (`/trends` 두 번째 카드)

성분 관심도(15번)는 "무엇이 뜨는가"를 봅니다. 이건 **"어디로 얼마나 나가는가"**입니다.
위키백과 조회수 같은 대리 지표가 아니라 각국이 신고한 통관 실적입니다.

### 22-1. 출처 — UN Comtrade (키 불필요)

```
https://comtradeapi.un.org/public/v1/preview/C/A/HS
  ?reporterCode=410&period=2025&flowCode=X&cmdCode=3304
```

- `public/v1/preview` 는 **API 키 없이** 열려 있는 경로입니다 (한 번에 500건 제한)
- 상대국 코드표는 `files/v1/app/reference/partnerAreas.json` 에서 받아 국기·이름에 씁니다
- 대상: 대한민국(410) 신고분, 수출(X)·수입(M), 최근 3개 연도

| HS | 품목 |
|---|---|
| 3303 | 향수·화장수 |
| 3304 | 기초·색조 |
| 3305 | 두발용 |
| 3307 | 면도·목욕·데오드란트 |

비누(3401) 같은 생활용품은 뺐습니다. 화장품이 아닙니다.

### 22-2. 수집 (`trade_store.py`)

블록 하나 = **연도 × 수출입 × HS 코드**. 전부 3 × 2 × 4 = **24블록**입니다.

```bash
python trade_store.py              # 전부 수집 (약 40초)
python trade_store.py --force      # 캐시를 무시하고 다시 수집
python trade_store.py --no-mirror  # 미러 보완 없이
```

화면의 **통계 수집** 버튼은 한 번에 6블록씩만 받습니다(네 번 누르면 끝).
캐시는 `tradedata/comtrade.json` (`.gitignore` 대상), TTL 20일입니다.
연 단위 통계라 자주 받을 이유가 없습니다.

`cmdCode` 는 `3303,3304,3305,3307` 처럼 묶을 수도 있지만 **그러면 500건에서 잘립니다**
(수출 4개 코드 합치면 정확히 500건에서 끊겼습니다). 그래서 코드별로 따로 받고,
`len(data) >= 500` 이면 `truncated` 로 표시해 화면에 경고를 띄웁니다.

### 22-3. 결측치 처리 — 0과 모름은 다르다

이 기능에서 제일 중요한 부분입니다. 무역 통계는 반드시 구멍이 납니다.
빈 칸을 0으로 덮으면 화면에서는 **거래가 끊긴 나라**로 보이는데,
실제로는 신고가 안 된 것뿐인 경우가 많습니다.

기준은 하나입니다. **Comtrade 는 거래가 없는 상대국을 아예 싣지 않습니다.**
그 해 통계를 들고 있는데 나라 이름이 없으면 거래가 없었던 것이고(=0),
통계 자체가 없으면 모르는 것입니다. 둘을 같은 칸에 그리면 안 됩니다.

| 상태 | 뜻 | 합계·증감률 |
|---|---|---|
| `신고` | 한국 통관 신고값 그대로 | 포함 |
| `실적 없음` | 그 해 통계에 이 나라가 없음 = 거래 없음(0) | 포함 |
| `미러` | 우리 쪽엔 빠졌는데 상대국이 신고한 값 | 포함 |
| `수집 중` | HS 코드 일부만 받아 둔 상태라 실제보다 작다 | **제외** |
| `보간` | 앞뒤 연도 사이를 선형 보간 | **제외** |
| `미보고` | 메우지 않음. 0이 아니라 모름 | **제외** |

- **보간은 가운데만** 합니다. 양 끝은 건드리지 않습니다 —
  끝을 늘리는 건 보간이 아니라 예측이고, 여기서 할 일이 아닙니다
- **증감률은 두 해 모두 실측일 때만** 냅니다. 아니면 `비교 불가`.
  보간값끼리 비교하면 만들어 낸 숫자로 만들어 낸 추세를 그리게 됩니다
- **미러 통계** — 우리 통계에서 사라진 나라를 상대국 신고로 다시 확인합니다.
  상대국도 신고가 없으면 진짜 거래 중단이고, 값이 있으면 우리 쪽 누락입니다.
  한 번에 8곳까지, 직전 연도 규모가 큰 곳부터 봅니다
- **집계 코드 제외** — `Areas, nes`·`Bunkers`·`Free Zones` 같은 비국가 코드는 순위에서 뺍니다.
  다만 `Other Asia, nes`(490)는 사실상 대만이고 실제 거래처라, 빼지 않고 이름만 밝혀 둡니다
- **올해 실적은 없습니다.** 연 단위 통계라 아직 안 올라옵니다. 최근 3개 연도만 씁니다
- kg당 단가는 신고 중량이 있을 때만 냅니다. 없으면 `—`

처리 결과는 화면 아래 **결측치 처리** 상자에 칸 수로 그대로 보여 줍니다.
숨기지 않는 것이 요점입니다.

## 23. 화면을 묶음으로 나눔 (`_switch.html`)

오늘의 트렌드에 수출입 통계를 붙이고 나니 한 화면이 **6.6화면**이 됐습니다.
성분 표를 보려고 들어와서 수출입 표까지 지나쳐 내려야 하는 건 화면 잘못입니다.
그래서 성격이 다른 묶음은 쌓지 않고 **하나씩** 봅니다.

### 23-1. 방식 — 주소에 남는 탭

`templates/_switch.html` 의 `view_switch()` 매크로 하나로 씁니다.

```jinja
{% raw %}{% from "_switch.html" import view_switch %}
{{ view_switch('trends', view, [
     {'key': 'ingredient', 'icon': '🧪', 'label': '성분 관심도',
      'desc': '어떤 성분이 뜨고 지는가', 'badge': '12종', 'badge_css': 'live'},
     ...
   ], {'category': selected_category, 'hs': trade.hs}) }}{% endraw %}
```

- JS 토글이 아니라 **주소(`?view=`)** 로 갈라집니다.
  새로고침해도, 통계를 수집하고 돌아와도 보던 묶음이 그대로입니다
- 마지막 인자(`keep`)에 넣은 값은 링크마다 따라붙습니다.
  묶음을 옮겨도 고른 HS 코드·연도·카테고리가 풀리지 않습니다
- 묶음 안쪽 링크(수집 버튼, HS 탭, 연도 칩, 카테고리 탭)에도 `view` 를 넣어
  **한 번 고른 묶음에서 빠져나가지 않게** 합니다
- 라우트에서 허용 값을 검사합니다 (`TREND_VIEWS`, 이상한 값이면 기본 묶음)

### 23-2. 덤 — 안 보는 묶음은 받아오지 않는다

`/trends` 는 원래 들어올 때마다 위키미디어 API를 두드렸습니다(성분 관심도 갱신).
수출입 묶음을 보는 중에 그럴 이유가 없어서 `auto_refresh=(view == 'ingredient')`
로 막았습니다. 다른 묶음에서는 캐시만 읽습니다.

### 23-4. 긴 표는 끊는다 (`_pager.html`)

묶음을 나눠도 **표 자체가 길면** 소용이 없습니다. 규제 판정은 50행,
국가별 수출입은 204행이었습니다. 표는 나누는 게 아니라 끊어야 합니다.

```jinja
{% raw %}{% from "_pager.html" import pager as pager_bar %}
{{ pager_bar('trends', trade_pager,
             {'view': 'trade', 'hs': trade.hs}, unit='개국', param='trade_page') }}{% endraw %}
```

`app.paginate(rows, page)` 가 그 쪽 행과 페이지 바 값을 같이 돌려줍니다. 한 쪽 20행.

- **건수는 쪽이 아니라 걸러낸 전체 기준**으로 셉니다.
  "50건 중 21–40" 처럼 어디를 보고 있는지 같이 적습니다
- 쪽 번호는 양 끝과 현재 쪽 주변만 보여 주고 사이는 `…` 로 접습니다 (`1 … 4 5 [6] 7 8 … 20`)
- 검색 조건을 바꾸면 **1쪽으로 돌아옵니다** — 필터 폼에 `page` 가 없어서 자연히 그렇게 됩니다.
  3쪽을 보다가 조건을 바꿨는데 3쪽이 유지되면 빈 표가 나옵니다
- 주소 이름(`param`)을 바꿀 수 있습니다. 한 화면에 표가 둘 이상이면 섞이기 때문입니다
  (오늘의 트렌드는 `trade_page`)
- 규제 판정은 표로 바로 돌아오게 `#reg-list` 앵커를 붙였습니다.
  오늘의 트렌드는 묶음 전환 바가 맨 위라 앵커를 안 붙입니다

국가별 수출입은 원래 **상위 25곳만 잘라** 보여 줬는데, 그러면 정작 찾는 시장이

## 24. 고객사 엑셀 내보내기·가져오기 (`/customers/import`)

해외영업은 고객사 명단을 엑셀로 들고 다닙니다. 전시회에서 받아온 명함 정리표,
전임자에게 넘겨받은 목록 같은 것들입니다. 그걸 화면에서 한 명씩 다시 치게 하면
아무도 쓰지 않습니다.

**내보낸 파일과 올리는 양식이 같은 모양입니다.** 내려받아 고치고 다시 올리면
그대로 반영됩니다. 새 양식을 따로 외울 필요가 없습니다.

### 24-1. 엑셀 열 15개

`고객사 ID | 회사명* | 국가 | 도시 | 등급 | 담당 영업 | 담당자 | 직급·직함 | 역할 |
이메일 | 전화 | 시차 | 사용 언어 | 대표 | 메모`

- **한 줄 = 담당자 한 명**입니다. 같은 회사에 여러 명이면 회사명을 반복해 적습니다
- 담당자 칸을 비우면 **회사만** 등록됩니다
- 열 순서를 바꿔도 되고 모르는 열이 끼어 있어도 됩니다. **머리글 이름**으로 찾습니다
- 파일에는 `작성 안내` 시트가 같이 들어갑니다. 파일만 받아도 쓰는 법을 알 수 있게

### 24-2. 원하는 데이터만 골라 받는다

두 가지를 **따로** 고릅니다.

**① 누구를 받을지 (줄)**

| 조건 | 주소 | 쓰는 자리 |
|---|---|---|
| 직무(역할) | `role=buyer&role=qa` | 인증서 공지는 품질 담당에게만 |
| 이메일 있는 사람만 | `email=1` | 메일 발송 명단 |
| 전화번호 있는 사람만 | `phone=1` | 급할 때 거는 명단 |
| 대표 담당자만 | `primary=1` | 회사마다 한 명 |
| 그만둔 담당자 빼기 | `active=1` | 퇴사자 제외 |
| 사용 언어 | `lang=English` | 영문 안내문 발송 |
| 등급 · 국가 · 검색어 | `grade=vip&country=미국&q=…` | 회사 쪽 조건 |

직무가 이 필터의 핵심입니다. 인증서 재발급 공지를 구매 담당에게 보내면 품질
담당에게 다시 돌아오고, 선적 지연 안내를 품질 담당이 받으면 아무 일도 일어나지
않습니다. 명단은 **보낼 사람 단위**로 뽑아야 쓸모가 있습니다.

체크박스 옆에 **지금 몇 명인지** 같이 띄웁니다. 물류 담당이 0명이면 눌러 보기
전에 압니다.

**② 어떤 값을 받을지 (열)** — 15개 중 체크로 고릅니다.

**자주 쓰는 조합** 버튼은 ①과 ②를 한 번에 정합니다.

| 조합 | 누구를 | 어떤 값 |
|---|---|---|
| 전부 | 모든 담당자 | 15개 전부 |
| 메일 발송용 | 이메일 있는 사람만 | 회사·담당자·이메일·언어 |
| 구매 담당 | 역할 = 구매·발주 | 회사·국가·담당자·직급·이메일·전화 |
| 품질·인증 담당 | 역할 = 품질·인증 | 〃 |
| 물류 담당 | 역할 = 물류·선적 | 〃 |
| 대표 담당자만 | 대표로 지정된 사람 | 회사·국가·담당자·직급·역할·연락처 |
| 회사만 | (담당자 없음) | ID·회사·국가·도시·등급·담당 영업 |

지켜야 할 것들:
- **회사명은 늘 들어갑니다.** 고쳐서 다시 올릴 수 있어야 하는데, 회사명이 없으면
  어느 회사 얘기인지 알 길이 없습니다
- 담당자 열을 하나도 안 고르면 **회사 단위로 접습니다.**
  담당자가 셋이라고 같은 회사가 세 줄 나오면 그건 회사 명단이 아닙니다
- 직무로 좁혀 놓고 한 명도 안 걸린 회사는 **아예 뺍니다.** 빈 줄로 내보내면
  "이 회사에도 품질 담당이 있다"는 착각을 줍니다
- **파일명에 무엇을 뽑았는지 남깁니다** — `고객사_품질인증_20260919.xlsx`.
  받은 사람이 파일 이름만 보고 알 수 있어야 합니다
- `조건만 다시 세기` 를 누르면 내려받기 전에 몇 곳 · 몇 줄인지 먼저 보여 줍니다.
  0줄이면 "머리글만 있는 파일이 됩니다" 라고 미리 알려 줍니다
- 줄 수는 **서버에서** 셉니다. 화면에서 대충 센 숫자와 받은 파일이 다르면 안 됩니다

주소로도 부를 수 있습니다:
`/customers/export?role=qa&email=1&country=미국&cols=company&cols=name&cols=email`

### 24-3. 올리면 먼저 판정만 보여 준다

올리자마자 저장하지 않습니다. 한 줄씩 무엇이 될지 보여 주고 **확인을 눌러야**
들어갑니다. 명단은 잘못 들어가면 되돌리기가 번거롭습니다.

| 판정 | 뜻 |
|---|---|
| `담당자 추가` | 새 담당자. 회사가 없으면 회사도 같이 만듭니다 |
| `담당자 갱신` | 같은 회사 + 같은 이메일이라 기존 담당자를 고칩니다 |
| `회사만 등록` | 담당자 칸이 비어 회사만 만듭니다 |
| `회사 정보 갱신` | 엑셀로 등록했던 회사의 빈 칸을 채웁니다 |
| `변경 없음` | 이미 있는 고객사이고 바뀌는 게 없습니다 |
| `오류` | 저장에서 빠집니다. 사유를 같이 적습니다 |

잡아내는 오류:
- 회사명이 비었음
- 이메일 형식이 아님
- 같은 담당자가 파일 안에 두 번
- 적어 넣은 `고객사 ID` 가 없음

지켜야 할 것들:
- **빈 칸은 지우라는 뜻이 아닙니다.** 엑셀에 안 적은 값은 원래대로 둡니다
- 회사명은 **대소문자·공백·전각 차이를 무시**하고 맞춥니다.
  `Nordic Glow AB` 와 `nordic glow ab` 는 같은 회사입니다
- 같은 파일에 같은 새 회사가 여러 줄 있어도 **회사는 한 번만** 만듭니다
- 같은 파일을 두 번 올려도 담당자가 두 배가 되지 않습니다. 두 번째는 전부 `갱신` 입니다

### 24-4. 엑셀로 올라온 고객사

기존 고객사 카드는 더미(`dummy_data._CUSTOMER_PROFILES`)라 엑셀에서 온 회사를
담을 곳이 없었습니다. `customer_store.py`(SQLite `data/customers.db`)를 새로 두고,
고객사 목록·상세는 **더미 카드 + 엑셀로 올린 회사**를 합쳐 보여 줍니다.

- 요청사항·메일 이력·거래 통계는 엑셀에 없습니다. **빈 채로 둡니다.** 지어내지 않습니다
- 고객사 id 는 회사명에서 만듭니다 (`Nordic Glow AB` → `nordic-glow-ab`).
  알파벳이 안 남는 이름이면 `cust-xxxxx`, 겹치면 뒤에 번호를 붙입니다
- 목록 요약의 `등록 고객사` 에 같이 셉니다

### 24-5. 아직 안 한 것
- **.xls (구버전)** 은 못 읽습니다. 저장할 때 .xlsx 로 바꿔야 합니다
- 화면에서 고객사를 직접 등록·수정하는 기능 (엑셀로만 들어옵니다)
- 가져오기 되돌리기 (지금은 미리보기에서 확인하는 것으로 갈음합니다)
- 담당자 삭제는 엑셀로 안 됩니다. 빈 칸을 지우라는 뜻으로 받지 않기 때문입니다

### 25-3. 갱신 방식

| 출처 | 주기 | 이유 |
|---|---|---|
| BLS | 하루 1회 | 월간 지수다. 하루 한 번이면 새 발표·수정을 놓치지 않는다 |
| Metals.Dev | 하루 2회 | 무료 한도 월 100회. 하루 2회면 월 최대 62회 |

- **사용자가 접속할 때마다 외부 API 를 부르지 않습니다.** 화면은 서버가 받아 둔
  SQLite(`data/packaging.db`)만 읽습니다. 수집은 `지금 수집` 버튼이나 CLI 로 합니다
- Metals.Dev 는 **재시도까지 한도에 포함**해 세고, 월 80회에서 스스로 멈춥니다.
  화면에 `이번 달 호출 n/80회` 로 띄웁니다
- **서버 수집 시각**과 **데이터 기준일**을 따로 적습니다. 둘은 다른 값입니다
- 월간 지수를 `실시간 시세` 라고 부르지 않습니다. `월간` / `하루 2회 업데이트` 로 적습니다

```bash
python packaging_store.py           # 받을 때가 된 것만
python packaging_store.py --force   # 주기를 무시하고 지금
python packaging_store.py --status  # 받아 둔 상태만 보기
```

고무 지수가 따라붙으면 안 됩니다.

### 25-5. 데이터 처리 규칙

- **없는 과거를 만들지 않습니다.** 받아 둔 만큼만 그립니다
- **기준값이 없으면 변화율을 내지 않습니다.** 12개월 전 값이 없으면
  전년 동월 비교를 아예 표시하지 않습니다
- **오류를 0 이나 더미로 바꾸지 않습니다.** 실패하면 마지막 정상값과 그 기준일을
  그대로 두고 상태만 `수집 실패` 로 바꿉니다
- **같은 기준일은 덮어씁니다.** (`material`, `period`) 가 기본키라 같은 달이 두 줄이
  되지 않고, 값이 바뀐 경우(수정 발표)만 고치면서 `수정 반영` 시각을 남깁니다
- **소재 상승률을 평균 내지 않습니다.** 소재마다 용기에서 차지하는 비중이 달라
  "포장비 몇 % 인상" 같은 숫자를 여기서 만들면 틀립니다
- 연간 평균(`M13`)은 건너뜁니다. 월간 계열만 씁니다

확인한 것 (실제로 돌려 봤습니다):

| 검증 | 결과 |

### 26-1. LLM 이 아닙니다

## 27. 프로젝트 - 업무 흐름을 하나로 묶기 (`/projects`)

여기까지 만든 화면은 각각 잘 돌지만 **서로 남남이었습니다.** 요청서를 분석한 결과가
견적 화면으로 이어지지 않고, 샘플 피드백은 어디에도 안 남고, 일정은 따로 놀았습니다.

이 단계의 목표는 화면을 예쁘게 만드는 게 아니라 **한 건이 처음부터 끝까지 이어지는지**를
검증하는 것입니다. 완성형 서비스가 아니라 **기능 중심 시제품**입니다.

```
바이어 요청 접수 → 요청서 분석 → 바이어 확인사항 → 연구소·공장 전달
→ 샘플 제작·피드백 → 견적 비교 → 일정 관리 → 후속 연락
```

### 27-1. 값의 상태 — 이 시제품의 뼈대

시제품에서 제일 위험한 건 **예시로 깔아 둔 숫자를 확정값으로 착각하는 것**입니다.
그래서 모든 값에 어디서 온 값인지를 붙입니다.

| 상태 | 뜻 |
|---|---|
| `예시 데이터` | 시연용으로 깔아 둔 값. 실제 값이 아님 |
| `기본값` | 시스템 기본값. 확인하고 고쳐 써야 함 |
| `분석 결과` | 요청서에서 읽어낸 값 |
| `확인 필요` | 빠졌거나 애매해서 바이어·담당자 확인이 필요 |
| `사용자 입력` | 담당자가 직접 넣은 값 |
| `확정값` | 양쪽이 합의해 확정한 값 |

제품 조건 23칸마다 이 뱃지가 붙고, 견적 대안에는 `실제 원가` / `기본 예시값`이 붙습니다.

### 27-2. 프로젝트 통합 화면 (`/projects/<id>`)

한 건에 딸린 것을 한 화면에서 봅니다.

고객사·바이어 / 제품명·판매국 / 원문 요청서 / 추출된 제품 조건 / 확인이 필요한 항목 /
연구소 전달 문서 / 공장 생산 검토 문서 / 샘플 버전과 피드백 / 원가와 견적 조건 /
프로젝트 일정 / 담당자와 다음 할 일 / 현재 상태와 진행률.

**진행률은 사람이 체크하는 게 아니라 값이 실제로 들어왔는지로 판정합니다.**

| 단계 | 끝났다고 보는 조건 |
|---|---|
| 요청 접수 | 고객사·제품이 적혀 있다 |
| 요청서 분석 | 제품 조건이 5개 이상 들어왔다 |
| 확인사항 정리 | 확인사항이 있고 미해결이 0건이다 |
| 연구소·공장 전달 | 원문이 있어 전달 문서를 만들 수 있다 |
| 샘플·피드백 | 샘플이 1건 이상 있다 |
| 견적 비교 | 견적 대안이 2개 이상이다 |
| 일정 관리 | 일정이 걸려 있다 |
| 후속 연락 | 연락 이력이 있다 |

시제품의 진행률은 그래야 믿을 수 있습니다.

### 27-3. 바이어 확인사항과 회신 초안 (`/projects/<id>/questions`)

요청서에서 **빠진 조건**을 자동으로 모읍니다 — 통화·Incoterms·결제조건·MOQ·납기·
용기 사양·용기 수급·라벨·요구 서류. 실무에서 이게 비어 있으면 견적이 한 번 더 왔다 갔다 합니다.

- 항목을 고르면 **영문 확인 메일 초안**이 만들어집니다 (미리 적어 둔 문장을 엮습니다.
  `TODO: 실제 연동` — 문장 다듬기는 아직 사람이 합니다)
- **고객사 과거 요청과 충돌하면 함께 표시합니다.** 낱말이 맞부딪치는 경우만 짚고
  판단은 사람이 합니다. 예: 과거 "전 제품 무향 유지" ↔ 이번 "Soft citrus & floral 0.3%"
- 회신을 적으면 그 값이 **제품 조건에 확정값으로 올라가고** 확인사항에서 빠집니다
- 다른 화면에서 값이 확정되면(견적 대안 선택 등) **열려 있던 확인사항이 자동으로 닫힙니다**

### 27-4. 샘플 피드백 (`/projects/<id>/samples`)

`1차 A` · `1차 B` · `2차 A` 처럼 차수와 버전을 나눕니다.
같은 칸에 기록해야 나중에 **어디서 갈렸는지** 찾을 수 있습니다.

기록 항목: 제형 · 향 · 색상 · 점도 · 용기 · 사용감 · 규제 이슈 · 원가

피드백은 **바이어 / 내부 검토**로 나누고 판정(좋음·수정 요청·부적합·참고)을 답니다.
피드백이 들어오면 샘플 상태가 따라 움직입니다 (수정 요청 → `revise`).
상태: 제작 중 → 발송함 → 피드백 받음 → 수정 요청 → 승인.

### 27-5. 견적 대안 비교 (`/projects/<id>/quotes`)

수량·용기 사양·거래조건·마진율을 바꿔 가며 나란히 봅니다.

```
5,000개  · 기본 용기 · FOB → USD 1.62
10,000개 · 기본 용기 · FOB → USD 1.53  (최저)
5,000개  · 고급 용기 · CIF → USD 1.89
```

- 각 값이 **실제 원가인지 기본 예시값인지** 끝까지 달고 다닙니다
- 물류비는 조건별 기본 예시값(FOB 110원 · CIF 260원/개), 고급 용기는 용기 원가 +35% 가정입니다.
  **이 표로 고객에게 견적을 내지 않습니다** — 정식 견적서는 영업단가 계산 화면에서 뽑습니다
- 대안을 고르면 수량·조건·통화가 **제품 조건에 확정값으로** 올라갑니다

### 27-6. 일정과 후속 연락

일정은 새로 만들지 않고 **기존 일정관리(19번)에 건을 만들어 연결합니다.**
단계(개발요청 전달 → 규제·처방 검토 → 샘플 제작 → … → 선적)가 이미 이 업무 흐름과 같습니다.

바이어 연락 이력과 **다음 연락일**을 같은 프로젝트에서 기록합니다.
예정일이 지나면 `다음 할 일` 맨 위에 ⏰ 로 올라옵니다.
허브의 `바이어 연락` 칸은 요약이고, `전체 보기` 를 누르면
연락 기록과 **주고받은 메일**이 같이 있는 화면이 열립니다 (30번 참고).

### 27-7. 기존 화면과 잇기

화면을 새로 만들지 않고 **주소에 `?project=` 를 붙여** 기존 화면을 그 건의 맥락으로 엽니다.

| 화면 | 프로젝트에서 열면 |
|---|---|
| `/convert?project=` | 그 건의 고객사·파일로 맞추고 단계를 `전달`로 옮김 |
| `/pricing?project=` | 고객사·제품·수량(MOQ)·통화·Incoterms·목표 단가를 받아 시작 |
| `/packaging?project=` | 그 건에 저장한 포장 구성의 소재만 표시 |

각 화면 위에는 **"○○ 프로젝트에서 열었습니다 · 돌아가기"** 띠가 붙습니다.

### 27-8. 챗봇도 프로젝트를 본다

프로젝트 화면에서 물으면 **그 건의 값으로** 답합니다.
어느 건인지 모르면 아무 건이나 골라 답하지 않습니다.

- "이 건 어디까지 왔어?" → 8단계 진행 상황
- "확인사항 뭐 남았어?" → 미해결 항목 (충돌은 ⚠ 표시)
- "샘플 어떻게 됐어?" → 차수·버전·상태·최근 피드백
- "견적 대안 비교해줘" → 대안별 단가와 값 출처

### 27-9. 아직 안 한 것

- 원문 요청서 업로드가 프로젝트로 바로 들어오는 경로 (지금은 샘플 요청서로 시작합니다)
- 전달 문서의 **스냅샷 보관** (지금은 열 때마다 다시 만듭니다)
- 견적 대안 → 정식 견적서 자동 채우기 (지금은 화면만 넘어갑니다)
- 프로젝트별 권한·담당자 배정

## 28. 아마존 화장품 순위 · 매거진 소식 (`/trends` → 🏆 묶음)

성분 관심도(15번)가 검색·조회수라면, 이건 **실제로 팔리는 물건의 순서**입니다.
바이어에게 "이런 게 올라오고 있습니다"라고 말할 때 쓰는 숫자입니다.

### 28-1. 아마존을 어떻게 다뤘나 — 먼저 확인한 것

시작 전에 세 가지를 실제로 확인했습니다.

| 확인 | 결과 |
|---|---|
| `robots.txt` 가 베스트셀러 경로를 막는가 | **막지 않습니다** (`/gp/bestsellers/beauty/` 허용) |
| 정직한 UA(도구 이름을 밝힘)로도 응답하는가 | **200, 차단 화면 없음** |
| 공식 경로가 있는가 | **있습니다** — Product Advertising API |

robots.txt 는 허용하지만 **아마존 이용약관은 자동 수집을 제한**합니다.
(아마존 404 페이지도 "automated access 는 api-services-support 로 문의하라"고 적어 둡니다.)

그래서 **기능은 만들되 기본을 꺼 뒀습니다.** 켤지 여부는 회사가 판단할 일이라
`.env` 에 `AMAZON_RANK_ENABLED=1` 을 넣어야 돕니다. 화면에도 왜 꺼져 있는지 적습니다.

FDA 때(21번)와 같은 규칙입니다 — **막으면 우회하지 않습니다.**
켜고 수집하다가 아마존이 로봇 확인 화면을 띄우면 그 자리에서 멈추고
`수집 차단됨` 으로 표시합니다.

켜더라도:
- **하루 1회**, 카테고리 4개를 **3초 간격**으로
- 받는 값은 **순위 · 제품명 · ASIN** 뿐 (이미지·가격·리뷰는 안 받습니다)
- 스냅샷은 45일만 보관

### 28-2. 무엇을 보여주나

카테고리 4개: 뷰티 전체 / 스킨케어 / 메이크업 / 헤어케어 (각 30위)

  아마존이 주는 값이 아닙니다. 첫 수집이면 변동을 표시하지 않습니다
- **한국 브랜드로 보이는 것** — 제품명에 K-뷰티 브랜드 이름이 있으면 셉니다.
  `추정값`이라고 적습니다. (실제 수집에서 뷰티 전체 30위 중 3개)

  "요즘 뭘 내세우나"를 봅니다. ODM 영업이 쓰는 각도입니다

주의 문구를 화면에 답니다: 미국 아마존 **한 채널의 순위**일 뿐 시장 점유율이 아니고,

**지어내지 않는 규칙:**
- 비교할 이전 수집이 없으면 **변동 이야기를 만들지 않습니다.**
  "비교할 이전 수집이 없어 변동을 말할 수 없습니다" 라고 적습니다
- 매거진에 겹치는 낱말이 없으면 없다고 적습니다
- 브랜드·낱말은 제목에서 뽑은 `추정값`이라고 매번 답니다

챗봇에서도 부를 수 있습니다 — "아마존 순위 요약해줘", "스킨케어 순위는?",
"요즘 뭐가 잘 팔려?"

`TODO: 실제 연동` — LLM 을 붙이더라도 **근거 줄은 그대로 달아야 합니다.**
근거 없는 요약은 시제품에서 제일 위험합니다.

### 28-6. 아직 안 한 것
- **Movers & Shakers**(급상승) — 화면 구조가 달라 아직 못 읽습니다
- 가격·리뷰 수 — 받지 않습니다. 순위만 봅니다

## 29. 견적환율 조회 (`fx_store.py` · 영업단가 계산 ④)

견적환율을 손으로 적으면 늘 두 가지가 어긋납니다.

- 어제 값을 그대로 쓰다가 오늘 단가가 틀어집니다
- "그때 환율로 계산한 겁니다" 라고 말해도, **그때가 언제인지** 서로 다르게 압니다

그래서 값만 받지 않고 **어느 기관의 · 언제 자 · 어떤 기준** 환율인지를
값과 같이 들고 다닙니다. 견적서(사내 보관용)에도 같이 찍힙니다.

### 29-1. 기준 세 가지

| 기준 | 언제 쓰나 |
|---|---|
| **최근 고시** | 지금 단가를 뽑을 때 |
| **특정 날짜** | 계약일·발주일·선적일 기준으로 다시 따질 때 |
| **기간 평균** | 월평균환율처럼 한 달을 묶어 단가를 잡을 때 |

기간 평균은 `최근 1·3·6개월 / 전월(1일~말일) / 직접 지정` 중에 고릅니다.

### 29-2. 출처 두 곳

| 출처 | 키 | 주는 것 |
|---|---|---|
| **ECB 참고환율** (Frankfurter) | 불필요 | 최근·과거·시계열 전부 |
| **한국수출입은행 고시환율** | 필요 (`.env`) | 매매기준율 · TTB · TTS |

ECB 쪽은 **은행 고시환율이 아닙니다.** 유럽중앙은행이 매 영업일 한 번 내는
참고값이라고 화면에 적어 둡니다. 실제 입금 환율과는 차이가 납니다.

수출입은행 쪽은 키가 없으면 목록에서 고를 수 없게 막고 `API 키 필요`라고
적습니다. 조용히 다른 값으로 바꿔치기하지 않습니다.

```
# .env
KOREAEXIM_API_KEY=
```
발급: https://www.koreaexim.go.kr/ir/HPHKIR019M01 (무료, 하루 1,000회)
이 프로젝트는 하루 300회까지만 씁니다.

수출입은행은 **기간 평균을 지원하지 않습니다.** 하루치만 주는 API 라
한 달 평균을 내려면 20여 번을 불러야 합니다. 한도를 그렇게 쓰지 않습니다.
그래서 그 출처를 고르면 '기간 평균'이 목록에서 사라집니다.

### 29-3. 값의 상태

환율 값 옆에 늘 뱃지가 붙습니다.

| 뱃지 | 뜻 |
|---|---|
| `고시값` | 요청한 날짜에 실제로 고시된 환율 |
| `직전 영업일` | 그날은 고시가 없어(주말·공휴일) 앞 영업일 값을 가져옴 |
| `기간 평균` | 기간 중 고시된 날만 평균 |
| `수기 입력` | 담당자가 직접 적음 |
| `내장 기본값` | 아직 조회 전. 화면에 깔아 둔 값 |
| `환산 없음` | 원화 결제 |
| `API 키 필요` / `고시 없음` / `조회 실패` | 값을 못 구함 — **값을 건드리지 않음** |

손으로 고치면 뱃지가 `수기 입력`으로 바뀝니다. 고시값인 척하지 않습니다.

### 29-4. 결측치 처리

- **주말·공휴일은 고시가 없습니다.** 지어내지 않고 직전 영업일 값을 가져온 뒤
  "9월 13일은 고시가 없어 9월 11일 값을 가져왔습니다" 라고 적습니다
- **평균은 실제 고시된 날만** 평균 냅니다. 빠진 날을 보간하지 않습니다.
  몇 일치를 평균했는지, 기간 중 최저·최고가 얼마였는지 같이 적습니다
- 평일 수의 60% 도 안 되면 "아직 덜 받아 왔을 수 있습니다" 라고 밝힙니다
- **조회에 실패하면 값을 건드리지 않습니다.** 0 이나 지어낸 숫자로 덮지 않고
  상태만 바꿉니다
- **미래 날짜는 거절합니다.** 미래 환율은 알 수 없습니다

한 가지 함정이 있었습니다. Frankfurter 는 시작일이 주말이면 **그 앞 영업일을
하나 끼워 줍니다.** 8월 1일이 토요일이면 7월 31일이 같이 옵니다. 그대로
평균 내면 "8월 평균"에 7월이 섞입니다. 받아서 저장은 하되 평균은 날짜로
걸러 낸 것만 씁니다 (8월 22일치 → 21일치, 8.8433 → 8.8354원/엔).

엔화도 함정입니다. 수출입은행은 `JPY(100)` 으로 **100엔 단위**로 고시합니다.
그대로 쓰면 단가가 100배 틀어집니다. 1엔 기준으로 나눠서 넣습니다.
(위안화는 코드가 `CNH` 입니다)

### 29-5. 언제 외부를 부르나

**화면을 여는 것만으로는 부르지 않습니다.** 서버가 받아 둔 값으로 시작합니다.

- `환율 불러오기` 를 누를 때
- 결제 통화를 바꿀 때 (이전 통화 환율이 남아 있으면 단가가 엉뚱해집니다)

받아 둔 값은 `data/fx.db` 에 남습니다(Git 제외). 지나간 날짜의 고시는 다시
바뀌지 않으니 한 번 받으면 그대로 씁니다. 최근 고시만 세 시간마다 다시 봅니다.

```
python fx_store.py            # 오늘 자 환율을 미리 받아 둡니다
python fx_store.py --status   # 받아 둔 상태만 봅니다
```

### 29-6. 실무에서 한 가지

수출입은행을 쓰면 매매기준율과 함께 **전신환 매입률(TTB)** 을 같이 적어 줍니다.
수출대금은 매매기준율이 아니라 TTB 로 들어옵니다. 단가는 매매기준율로 잡더라도
실제 입금액을 따질 때는 TTB 를 봐야 합니다. 그 한 줄을 화면에 적어 둡니다.

### 29-7. 아직 안 한 것
- 한국은행 ECOS 연동 (별도 키가 필요합니다)
- 관세청 주간 과세환율 (수입 신고가 이 프로젝트 범위 밖입니다)
- 선물환·환헤지 계산
- 환율 변동 알림

## 30. 연락 기록 — 회사 단위와 건 단위를 나눔

이메일 히스토리가 고객사 화면에 있었습니다. 본문·첨부·번역·요약까지 다 펼쳐져
있으니 정작 **"이 회사와 최근에 무슨 얘기가 오갔나"** 가 안 보였습니다.
그리고 메일은 회사가 아니라 **그 건**에 딸린 것입니다. 같은 회사라도 A 건 메일과
B 건 메일이 한 줄로 섞여 있으면 어느 건 얘기인지 알 수가 없습니다.

그래서 둘로 나눴습니다.

| | 고객사 관리 (`?tab=log`) | 프로젝트 (`/projects/<id>/contacts`) |
|---|---|---|
| 단위 | 회사 | 그 건 |
| 담는 것 | 한 줄 메모 | 연락 기록 + 메일 원문 |
| 있는 것 | 담당자·방법·방향·날짜·메모 | 위 + 다음 연락일·다음 할 일 |
| 메일 본문 | 없음 (제목만) | 있음 (번역·요약 포함) |
| 저장 | `data/contact_log.db` | `data/projects.db` |

### 30-1. 고객사 연락 기록

한 줄이면 됩니다.

```
2026-09-20 · 📞 전화 · 받음 · Emily Park · 구매·발주
레티놀 농도 EU 기준 문의. 단가 조정 폭도 같이 물어봄
```

방법은 `📧 이메일 / 📞 전화 / 👥 미팅·화상 / 💬 메신저 / 📦 샘플 발송 / • 기타`.
프로젝트의 바이어 연락과 **같은 낱말**을 씁니다. 화면마다 다른 말을 쓰면
같은 기록인지 다른 기록인지 헷갈립니다.

담당자는 목록에서 고르되 **그때의 이름과 역할을 같이 적어 둡니다.**
그 담당자가 퇴사해 명단에서 빠져도 "누구와 한 연락인지" 는 남아야 합니다.
기록이 사라지면 안 됩니다.

메모가 비면 저장하지 않습니다. 날짜만 남은 줄은 쓸모가 없습니다.
남의 고객사 기록은 주소를 바꿔도 지워지지 않습니다 (`id` 와 `customer_id` 를 같이 겁니다).

고객사 화면에는 예전 메일이 **제목만** 남아 있습니다. 건별로 묶기 전에 쌓여 있던
것들이라 `예시 데이터` 라고 적어 둡니다.

### 30-2. 프로젝트 바이어 연락

허브의 `바이어 연락` 칸은 최근 네 줄 요약입니다. `전체 보기` 를 누르면:

- **연락 기록** — 담당자 · 방법 · 방향 · 날짜 · 내용 · 다음 연락일 · 다음 할 일
- **주고받은 메일** — 제목을 누르면 본문이 열리고 🌐 번역 / ✂️ 요약 (17번)
- 옆에 이 건의 담당자 목록

다음 할 일만 적고 날짜를 안 넣으면 `날짜 미정` 이라고 적습니다.
적은 내용이 조용히 사라지면 안 됩니다.

### 30-3. 옮기면서 고친 것

- `contacts_log` 에 `contact_id` · `person` · `role` 칸을 더했습니다.
  이미 만들어진 DB 는 `CREATE TABLE IF NOT EXISTS` 가 그냥 지나가므로
  `PRAGMA table_info` 로 확인해 `ALTER TABLE` 로 붙입니다 (`_add_missing_columns`)
- 채널에 `메신저` 를 더했습니다 (WhatsApp·WeChat·KakaoTalk 로 오는 연락이 많습니다)
- 잘못 적은 줄을 지울 수 있게 했습니다 (양쪽 다)
- 메일 열기·번역·요약 JS 를 고객사 화면에서 프로젝트 화면으로 옮겼습니다.
  고객사 화면에는 이제 메일 본문이 없어 그 JS 가 붙을 자리가 없습니다

### 30-4. 아직 안 한 것
- 실제 메일함(IMAP/Gmail API) 연동 — 메일은 아직 예시 데이터입니다
- 연락 기록에서 바로 프로젝트 만들기
- 고객사 목록에서 마지막 연락일로 정렬

## 31. 인증서 관리 (`/schedule?view=certs`)

인증서가 일정관리에 들어가 있는 이유는 하나입니다. **인증서는 만료됩니다.**
그리고 만료된 걸 선적 직전에 알면 그때는 이미 늦습니다.

### 31-1. 진짜 기한은 만료일이 아닙니다

```
갱신 착수일 = 만료일 − 준비기간
```

할랄 갱신 심사에 두세 달, ISO 22716 재심사는 실사 일정을 잡는 데만 몇 주가 듭니다.
만료일 D-7 에 알아차리면 인증서가 끊긴 채로 선적을 맞습니다.
그래서 **착수 권고일**을 따로 계산해 그날을 기한으로 봅니다.

> 만료 2026-12-05 · 갱신에 120일이 걸립니다. 착수 권고일(2026-08-07)이 지났습니다.

### 31-2. 세 갈래

| 갈래 | 무엇 | 예 |
|---|---|---|
| 🏭 **공장·시스템** | 우리 공장이 받는 인증. 모든 수출 건에 공통 | ISO 22716, CGMP, 할랄, 비건, COSMOS, Leaping Bunny |
| 🌍 **현지 등록·허가** | 파는 나라에서 **제품마다** 받는 것. 없으면 통관이 안 됨 | 중국 NMPA 비안·허가, EU CPNP·CPSR, 미국 MoCRA, 일본 제조판매업, 아세안 ACD, 대만 TFDA, 사우디 SFDA, EAEU EAC |
| 📄 **수출 서류** | 선적할 때 붙이는 증명서. 유효기간이 짧음 | CFS, CoA, MSDS, 동물실험 미실시 선언, C/O, 전성분표 |

목록에서 고르면 발급기관·유효기간·준비기간이 채워지고, 실무에서 자주 걸리는
지점을 💡 로 같이 띄웁니다.

> 💡 나라마다 인정하는 인증기관이 다릅니다. 말레이시아 JAKIM 을 인도네시아가
> 그대로 받아주지 않습니다. 파는 나라가 인정하는 기관인지 먼저 확인하세요

> 💡 중국 등 일부 국가는 **발급 6개월 이내** CFS 만 받습니다.
> 유효기간이 남아 있어도 다시 떼야 할 수 있습니다

미리 넣어 둔 유효기간·준비기간은 **업계 통상값**입니다. 인증기관이 정한 값이
아니라고 화면에 적고, 실제 인증서에 적힌 날짜로 고쳐 쓰게 합니다.

### 31-3. 기한 표시

| 뱃지 | 뜻 |
|---|---|
| `만료됨` | 유효기간이 지남. 이 인증서로는 선적할 수 없음 |
| `갱신 착수` | 지금 시작해야 만료 전에 끝남 |
| `만료 임박` | 60일 안에 만료 |
| `여유` | 아직 여유 있음 |
| `만료일 미확인` | 만료일을 안 적어 기한을 따질 수 없음 |
| `유효기간 없음` | 중국 비안·EU CPNP 처럼 기간 만료가 없는 등록 |
| `취득 준비 중` | 아직 받지 않은 인증 |

**`만료일 미확인` 과 `유효기간 없음` 은 다릅니다.** 앞은 확인이 필요한 것이고
뒤는 정상입니다. 둘을 같이 묶으면 확인해야 할 것이 묻힙니다.
그래서 목록에서 고른 인증서의 통상 유효기간이 0개월이면 `유효기간 없음`,
그렇지 않은데 날짜가 비어 있으면 `만료일 미확인` 으로 가릅니다.

### 31-4. 결측치 처리

- **만료일을 모르면 지어내지 않습니다.** `만료일 미확인` 으로 두고 D-day 를
  계산하지 않습니다. 등록할 때도 "모르면 비워 두세요 — 지어낸 날짜보다 낫습니다"
  라고 적습니다
- 발급일만 넣으면 통상 유효기간으로 만료일을 **추천**합니다.
  추천했다는 사실을 안내에 적고, 고쳐 쓰라고 말합니다
- **갱신은 날짜를 갈아 끼우는 일입니다.** 새 만료일이 없으면 갱신으로 처리하지
  않습니다. 상태만 `갱신 중` 으로 바꿔 두면 만료일은 그대로 남습니다
- 유효기간이 없는 등록을 만료 임박으로 몰지 않습니다

### 31-5. 일정과 섞이는 자리

- 요약 카드에 **인증서 갱신** 이 하나 늘었습니다 (만료 + 갱신 착수 + 임박)
- 탭 이름 옆에 건수 뱃지가 붙습니다
- **다른 탭에 있어도** 위에 띠로 뜹니다. 인증서가 끊기면 다른 일정이 다 맞아도
  선적을 못 하기 때문입니다

### 31-6. 저장
`data/certs.db` (SQLite, `.gitignore` 대상). 상태 변경에는 일정관리와 같은
세션 CSRF 토큰을 겁니다.

`예시 인증서 넣기` 를 누르면 만료된 것·착수해야 하는 것·여유 있는 것·날짜를 안
적은 것이 섞인 9건이 들어갑니다. 오늘을 기준으로 날짜를 만들어서 언제 눌러도
같은 모양이 나옵니다.

### 31-7. 아직 안 한 것
- **인증서 파일 보관** — 지금은 이름과 날짜만 다룹니다
- 만료 알림 메일·알림톡
- 프로젝트·고객사와 연결 (이 건에 필요한 인증서가 무엇인지)
- 수출국을 고르면 필요한 현지 등록을 자동으로 짚어 주기

## 32. 진행되지 않은 건 (`/projects` → 무산)

모든 건이 수주로 끝나지 않습니다. 오히려 대부분은 중간에 멈춥니다.
멈춘 건을 그냥 두면 목록에서 **진행 중인 것처럼 보이고**, 왜 안 갔는지는
담당자 머릿속에만 남습니다. 그 담당자가 바뀌면 내년에 같은 회사와 같은 일을
처음부터 다시 합니다.

### 32-1. 사유를 남기고 접습니다

프로젝트 화면 오른쪽 `이 건을 접기` 에서 사유를 고르고 메모를 답니다.
**지우지 않습니다.** 반년 뒤에 같은 고객사가 다시 오는 일이 흔해서,
`다시 열기` 한 번이면 그대로 살아납니다.

| 사유 | ⚑ |
|---|---|
| 연락 두절 | ⚑ |
| 정보만 받아감 | ⚑ |
| 샘플만 반복 수령 | ⚑ |
| 단가 합의 실패 · 수량(MOQ) 미달 · 사양 불일치 · 규제·인증 문제 · 납기 불가 | |
| 타사 선정 · 고객사 사정 · 우리 사정 · 기타 | |

⚑ 는 **진행 의사가 없었던 것으로 의심되는** 사유입니다.
**단가가 안 맞아 무산된 건 체리피커가 아니라 정상적인 협상 결과입니다.**
이 구분이 없으면 멀쩡한 고객사까지 싸잡게 됩니다.

### 32-2. 체리피커라고 단정하지 않습니다

같은 고객사의 건이 두 건 이상이면 프로젝트 화면 위에 **이력 카드**가 뜹니다.

```
Glowtree Beauty 와의 이력                          [참고]
무산 3건 중 2건이 연락 두절·정보 수집 쪽이고, 아직 수주가 없습니다.
샘플 2개·견적 3건이 나갔습니다.

  5건   0수주   2진행 중   3무산   2샘플   3견적
  [연락 두절 1] [정보만 받아감 1] [단가 합의 실패 1]
```

| 등급 | 조건 |
|---|---|
| `신호 없음` | ⚑ 사유 무산이 **2건 미만** |
| `참고` | ⚑ 사유 무산 2건 이상, 또는 3건 이상이어도 **수주 이력이 있음** |
| `주의해서 볼 신호` | ⚑ 사유 무산 3건 이상 **그리고** 수주 0건 |

지키는 것:

- **한 건 무산으로는 아무 말도 하지 않습니다.** 흔한 일입니다.
  그걸로 회사를 규정하면 멀쩡한 고객사를 잃습니다
- **수주 이력이 있으면 등급을 내립니다.** 거래는 되는 곳입니다
- 등급 이름이 `체리피커` 가 아니라 `주의해서 볼 신호` 인 것은 일부러입니다.
  숫자와 사유만 보여 드리고 판단은 담당자가 합니다
- 왜 그렇게 봤는지를 **항상 한 줄로 같이 적습니다**

### 32-3. 우리가 들인 것

체리피커의 실질 피해는 기분이 아니라 쌓인 숫자입니다.
그래서 건별로 **샘플 · 견적 · 연락** 건수를 세어 접기 칸 밑에 보여 주고,
고객사 이력 카드에서는 그 회사 전체로 합산합니다.

### 32-4. 모아 보기

목록의 `무산` 탭에 **사유 분포**가 뜹니다. 한 건씩 보면 안 보이는 게
모아 놓으면 보입니다 — 단가 때문에 지는지, 규제 때문에 막히는지,
연락이 끊겨 흐지부지되는지에 따라 다음에 할 일이 완전히 다릅니다.

### 32-5. 저장
`projects` 표에 `closed_reason` · `closed_note` · `closed_at` 을 더했습니다.
이미 만들어진 DB 는 `_add_missing_columns` 가 `ALTER TABLE` 로 붙입니다 (30-3 참고).
`무산` 은 상태 이름도 `종료` 에서 바꿨습니다 — 수주하고 끝난 건과 헷갈립니다.

### 32-6. 아직 안 한 것
- 무산 건을 일정관리에서 자동으로 정리하기
- 재접촉 시점 알림 ("6개월 뒤 다시 연락")
- 고객사 관리 화면에도 이력 카드 붙이기

## 33. 미국 규제 실데이터 (`us_reg_store.py`)

EU 는 부속서에 성분이 다 적혀 있어 대조가 단순합니다. **미국은 판정 방식이
거의 반대입니다.** 그래서 EU 코드를 그대로 쓸 수 없었습니다.

### 33-1. 미국은 "목록에 없으면 적합" 이 아닙니다

미국에는 **일반 화장품 성분의 사전 허가 목록이 없습니다.**
금지 조문에 안 걸린다는 건 "개별 금지 규정이 없다" 는 뜻이지 적합 판정이
아닙니다. MoCRA 에 따라 안전성 입증 책임이 제조사에 있습니다.
그래서 미등재 성분은 `적합` 이 아니라 **`주의`** 로 둡니다.

**색소는 정반대입니다.** 21 CFR 73·74 에 등재된 것만 쓸 수 있는
포지티브 리스트입니다. 등재돼 있어도 용도(눈가·외용·열거된 제품)가 갈리고,
**Part 74 색소는 FDA 배치 인증을 받은 로트만** 쓸 수 있습니다.
한국 업체가 자주 놓치는 지점이라 판정에 같이 적습니다.

### 33-2. 출처 — eCFR API (키 불필요)

```
https://www.ecfr.gov/api/versioner/v1/full/{date}/title-21.xml?part=N
```

전자 연방규정집의 공식 개발자 API 입니다. 웹페이지를 긁는 게 아니라
기관이 열어 둔 경로입니다. robots.txt 가 막는 곳(`/search`, `/compare`,
`/api/renderer`)은 건드리지 않습니다.

| 받아 오는 것 | 무엇 |
|---|---|
| 21 CFR 700 Subpart B | 화장품 금지·제한 성분 (수은·비티오놀·클로로포름 등) |
| 21 CFR 250 | 헥사클로로펜 등 |
| 21 CFR 73 Subpart C | 색소 — 배치 인증 면제 (29건) |
| 21 CFR 74 Subpart C | 색소 — 배치 인증 대상 (36건) |
| 21 CFR 740 | 경고 문구 |

조문 95건. 하루 한 번만 확인합니다.
**이 엔드포인트는 gzip 응답을 요구합니다** — `Accept-Encoding` 을 안 붙이면
406 이 떨어집니다.

```bash
python us_reg_store.py --force    # 지금 받아오기
python us_reg_store.py --status   # 받아 둔 상태 + CI 매핑 점검
```
화면의 `지금 받아오기` 버튼으로도 받습니다. 화면을 여는 것만으로는 부르지 않습니다.

### 33-3. CI 번호 ↔ 미국 명칭

EU·한국은 색소를 CI 번호로 적고 미국은 FD&C / D&C 이름으로 적습니다.
그래서 매핑 표를 두는데, **이건 참고 매핑이고 판정 근거는 조문 원문입니다.**

받아 온 조문과 대조해 보니 처음 적은 표에서 **세 군데가 틀려 있었습니다.**

| 잘못 적었던 것 | 실제 |
|---|---|
| `CI 17200` → D&C Red No. 31 | **No. 33** (74.2333) |
| `CI 77480` → Copper powder | 77480 은 **Gold**. 화장품용 목록에 없음 |
| `CI 45430` → 74.2303 | **그런 조문이 없음.** FD&C Red No. 3 은 1990년에 화장품 용도가 취소됨 |

실데이터를 쓰는 값이 이런 데서 나옵니다. 그래서 `--status` 가 매핑이 실제
조문을 가리키는지 매번 확인해 줍니다. 법이 바뀌어 표가 낡으면 조용히 못 찾고
지나가는데, 그건 "미등재" 와 구분이 안 되기 때문입니다.

**못 찾은 것과 쓸 수 없는 것도 가릅니다.** 취소된 걸 이미 아는 번호
(`CI_NOT_LISTED`)는 `사용 불가` 라고 단정하고, 그냥 못 찾은 색소는
`색소 등재 확인 필요` 로 둡니다.

### 33-4. 화장품과 의약품의 경계

미국에서 이 경계는 **성분과 효능 표방**으로 갈립니다. 시설 기준부터 달라집니다.

| 성분 | 판정 |
|---|---|
| 자외선차단 성분 (아보벤존·옥티노세이트·징크옥사이드 등) | SPF 를 표시하면 **OTC 의약품** (21 CFR 352). 한국의 기능성화장품이 여기서 갈립니다 |
| 하이드로퀴논 | **화장품 사용 불가.** 2020년 CARES Act 로 OTC 에서 빠져 처방 의약품입니다 |
| 미녹시딜 · 벤조일퍼옥사이드 · 불소 | OTC 의약품 성분 |
| 살리실릭애씨드 · 레조르시놀 | 각질 관리로 적으면 화장품, **여드름 효능을 표방하면 의약품** |

### 33-5. 판정에 늘 원문을 붙입니다

조문 번호와 원문 발췌를 같이 적습니다. 판정만 내놓고 근거를 숨기지 않습니다.

```
[BAN] Mercuric Chloride  사용 금지·제한   21 CFR 700.13 · Use of mercury compounds...
      21 CFR 700.13 에 금지·제한으로 등재된 성분입니다.
      원문: (b) The toxicity of mercury compounds is extensively documented...
```

이름 대조는 양방향으로 봅니다. 성분명이 조문 이름에 들어 있는 경우
(`Red No. 6` ⊂ `D&C Red No. 6 Lake`)와 조문 이름이 성분명에 들어 있는 경우
(`mercuric` ⊂ `Mercuric Chloride`)가 둘 다 있어서입니다.
한쪽만 보면 Mercuric Chloride 가 수은 조문에 안 걸립니다.
낱말 경계로 맞춰서 `Gold` 가 `Goldenrod Extract` 에 걸리는 일은 막습니다.

### 33-6. 저장
`data/us_reg.db` (SQLite, `.gitignore` 대상).
연방규정집이 스스로 밝힌 기준일(`up_to_date_as_of`)·마지막 개정일과
**우리가 받아 온 시각**을 따로 적습니다. 수집에 실패하면 이전 조문을
지우지 않고 그대로 둡니다. 다 받은 뒤에 한 번에 갈아 끼워서
중간에 실패해도 반쪽짜리가 남지 않습니다.

### 33-7. 아직 안 한 것
- 성분 작성 화면(16번)의 실시간 판정은 아직 EU 만 봅니다
- 21 CFR 352 (자외선차단 모노그래프) 원문은 받지 않습니다 — 성분 이름으로만 짚습니다
- MoCRA 시설등록·제품리스팅 상태는 인증서 관리(31번)에서 따로 봅니다
- 중국 NMPA · 일본 · 베트남은 여전히 더미입니다

## 34. 거래처 관리 — 고객사만 있는 게 아닙니다

`고객사 관리` 를 **`거래처 관리`** 로 바꿨습니다. 주소(`/customers`)는 그대로입니다.

해외영업 한 건이 돌아가려면 파는 쪽만으로 안 됩니다. 원료사·용기업체·임가공·
포워더·시험기관이 같이 움직입니다. 그런데 화면에는 바이어만 들어갈 수 있어서,
임가공 업체 담당자 연락처는 메신저를 뒤져야 했습니다.

### 34-1. 유형 일곱 가지

| 유형 | 무엇 | 쪽 |
|---|---|---|
| 🛍️ 고객사 (바이어) | 발주를 넣는 해외 브랜드·유통사 | 파는 쪽 |
| 🌏 현지 에이전트·유통 | 현지 수입자, EU 책임자(RP), 중국 경내책임자 | 파는 쪽 |
| 🧴 원료·부자재 공급처 | 벌크 원료, 용기·펌프·단상자 | 사는 쪽 |
| 🏭 하청·임가공 | 충전·포장 등 우리 대신 만드는 곳 | 사는 쪽 |
| 🚢 물류·포워더 | 선적·통관·내륙 운송 | 사는 쪽 |
| 🔬 시험·인증기관 | 안정성·미생물 시험, 인증 심사 | 사는 쪽 |
| 🏢 기타 | | |

**파는 쪽과 사는 쪽은 챙기는 게 다릅니다.** 파는 쪽은 등급·요청사항·견적이,
사는 쪽은 납기·단가·품질 이력이 중요합니다. 그래서 **등급(VIP·일반·신규)은
파는 쪽에만 띄웁니다** — 임가공 업체에 `VIP 고객사` 라고 적히면 우습습니다.
`거래 현황`(누적 발주·평균 회신)도 마찬가지로 파는 쪽에만 보여 줍니다.

목록 위에 유형 탭이 붙고, 요약 카드에 `파는 쪽 5 · 사는 쪽 4` 를 같이 적습니다.

### 34-2. 화면에서 바로 추가합니다

`＋ 거래처 추가` 버튼이 생겼습니다. 전에는 **엑셀로 올리는 길밖에 없었습니다.**
전시회에서 명함 한 장 받아 온 걸 넣으려고 엑셀을 만들게 하면 아무도 안 씁니다.

회사명만 있으면 등록되고, 바로 담당자 탭으로 넘어갑니다.

**같은 이름이 이미 있으면 새로 만들지 않고 그쪽으로 보냅니다.**
표기만 다른 같은 회사가 둘로 갈리면 연락 기록이 쪼개집니다.
예시 카드(Glowtree 등)와도 대조합니다.

유형을 잘못 골랐으면 상세 화면에서 바꿀 수 있습니다.
예시 카드는 저장할 곳이 없어 못 바꾸고, 화면에 그렇게 적습니다.

### 34-3. 엑셀에도 유형 칸

내보내기·양식·가져오기 모두 `유형` 열이 생겼습니다.
없으면 내보냈다 다시 올릴 때 임가공 업체가 전부 고객사로 되돌아갑니다.

엑셀에는 사람이 읽는 말로 적습니다 — `고객사 / 에이전트 / 원료·부자재 /
하청·임가공 / 물류 / 시험·인증 / 기타`. 아이콘이 붙어 와도 읽고,
못 읽으면 **빈 값으로 두어 기존 유형을 지키지** 지어내지 않습니다.

시트 이름도 `거래처·담당자` 로 바꿨지만, 예전 파일을 올려도 됩니다
(그 이름이 없으면 첫 시트를 읽습니다).

### 34-4. 저장
`customers` 표에 `kind` 칸을 더했습니다. 이미 만들어진 DB 는
`_add_missing_columns` 가 `ALTER TABLE` 로 붙입니다 (30-3 과 같은 방식).
`source` 로 **화면에서 등록한 것과 엑셀로 올린 것**을 구분합니다.

### 34-5. 아직 안 한 것
- 사는 쪽에 맞는 항목 (단가표, 납기 이력, 품질 문제 기록)
- 프로젝트에서 임가공·포워더를 골라 붙이기
- 원료사와 포장재 가격 동향(25번) 연결
- 거래처 유형별 담당자 역할 (지금은 역할 목록이 바이어 기준입니다)

## 35. 자사 정보 (`/company`)

견적서 · 프로포마 인보이스 · 커머셜 인보이스 · 패킹리스트 · 원산지증명 신청 ·
해외 등록 · 바이어의 거래처 등록 양식. **여기 들어가는 회사 정보는 전부 같은
값입니다.** 그런데 매번 예전 메일을 열어 복사하다 보면 영문 주소가 서류마다
조금씩 달라지고, 그게 통관에서 걸립니다.

한 군데 적어 두고 **서류가 여기서 읽어 갑니다.** 견적서의 공급자 칸은 이제
`company_store` 에서 옵니다.

### 35-1. 칸마다 "어디에 쓰이는지"를 적습니다

`왜 채워야 하나` 에 대한 답이라 화면에 같이 적습니다.

| 묶음 | 예 | 쓰이는 곳 |
|---|---|---|
| 🏢 회사 | 영문 상호, 대표자(영문), 사업자등록번호 | 견적서 · 인보이스 · C/O |
| 📍 주소 | 본사 영문, **공장 영문** | 공장 주소는 MoCRA 시설등록 · CPNP · 실사에 씁니다 |
| 📞 연락 | 전화 · 이메일 | 견적서 · 인보이스 |
| 🚢 수출 | 무역업고유번호, 원산지 표기, HS 코드 | 수출신고 · C/O · 라벨 |
| 💳 대금 수취 | 은행 · SWIFT · 계좌 | 인보이스 |
| 🙋 해외영업 담당 | 담당자(영문) · 직급 · 이메일 | 견적서 발행자 · 메일 서명 |

**영문 표기가 진짜입니다.** 국문은 우리끼리 보는 것이고 서류에 찍혀 나가는 건
영문입니다. 📄 표시가 붙은 칸이 그것이고, 비면 그 서류를 만들 수 없습니다.

### 35-2. 예시값을 입력값으로 착각하면 안 됩니다

칸마다 `입력값 / 예시 / 비어 있음` 을 붙이고, 위에 두 줄로 짚어 줍니다.

> **서류에 찍혀 나가는 칸 1개가 비어 있습니다** — 무역업고유번호.
> **10개 칸이 아직 예시값입니다** — 영문 상호 · 대표자(영문) · …
> 이대로 견적서를 내보내면 **남의 회사 이름이 그대로 나갑니다.**

빈 칸으로 저장하면 그 칸은 예시값으로 **돌아갑니다**. 그것도 화면에 적습니다.

### 35-3. 계좌는 다르게 다룹니다

바이어에게 주는 값이긴 하지만 화면에 그냥 깔아 두지 않습니다.

- 기본으로 **가려 두고** `가려 둔 값 보기` 를 눌러야 보입니다
- **견적서에는 넣지 않습니다.** 송금 정보는 인보이스에 들어갑니다
- **고치면 기록이 남습니다** (누가·언제·어느 칸).
  계좌만 바꿔치기해 보내는 사기 메일이 흔해서입니다
- `예금주(영문)는 영문 상호와 같아야 송금이 막히지 않습니다` 처럼
  실제로 걸리는 지점을 칸 밑에 적어 둡니다

### 35-4. 저장
`data/company.db` (SQLite, `.gitignore` 대상).
**입력값만 저장하고 예시값은 저장하지 않습니다.** 그래야 둘을 가릴 수 있습니다.

## 36. 거래처 상세 정비

`＋ 거래처 추가` 로 넣은 회사를 열면 화면이 거의 비어 있었습니다.
숫자와 태그는 예시 카드용이고, 정작 **고칠 수 있는 칸이 하나도 없었습니다.**

### 36-1. ⚙️ 정보 고치기 탭

유형 · 등급 · 국가 · 도시 · 담당 · 소통 채널 · 거래 시작 · 메모.
**여기 값만 실제로 저장됩니다.** 나머지 화면의 숫자·태그는 예시라고 적습니다.

예시 카드(Glowtree 등)는 저장할 곳이 없어 **폼을 통째로 잠그고** 그렇게 적습니다.
값은 보이되 바뀌지 않습니다.

빈 칸으로 두면 기존 값을 **지우지 않고 그대로 둡니다** — 엑셀로 다시 올릴 때
안 적은 칸이 지워지면 안 되기 때문입니다.

### 36-2. 📦 진행 건 — 실데이터

더미 목록을 읽던 것을 **실제 프로젝트**(`project_store`)로 바꿨습니다.
카드에 박아 둔 예시 목록과 실제 건이 따로 놀면 어느 쪽을 믿어야 할지 모릅니다.

건을 누르면 프로젝트로 넘어가고, `＋ 프로젝트 열기` 로 이 거래처의 새 건을
바로 만듭니다. 무산이 쌓이면 **거래 이력 카드**(32번)가 같이 뜹니다.

### 36-3. 📝 내부 메모 — 실제로 저장

전에는 화면에서만 붙고 새로고침하면 사라졌습니다. 이제 남습니다
(`contact_log.db` 의 `notes`).

연락 기록과 다릅니다.

| | 담는 것 |
|---|---|
| 📞 연락 기록 | 누구와 무슨 얘기를 했나 |
| 📝 내부 메모 | **다음 사람이 알아야 할 것** — 결제 습관, 회신이 늦는 시기, 깐깐한 부분 |

예시로 깔아 둔 메모는 아래에 `예시` 딱지를 붙여 따로 모읍니다.

### 36-4. 탭 순서
자주 쓰는 순서로 바꿨습니다 —
`담당자 · 연락 기록 · 진행 건 · 바이어 요청사항 · 내부 메모 · 정보 고치기`.
바이어 요청사항은 예시 데이터라 뒤로 보냈고, 비어 있으면
"건별 확인사항은 프로젝트에서 관리합니다" 라고 안내합니다.

### 36-5. 아직 안 한 것
- 거래 통계(누적 발주·평균 회신)는 여전히 예시입니다. 실제로 세려면
  발주·입금 기록이 있어야 합니다
- 특징 태그를 직접 달기
- 사는 쪽 거래처에 맞는 항목 (단가표, 납기 이력, 품질 문제)
